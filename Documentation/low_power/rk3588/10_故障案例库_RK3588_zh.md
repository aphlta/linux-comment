# RK3588 低功耗故障案例库

本文档 **优先收录可追溯来源的真实故障**（公开 commit、issue、内核邮件），每条给出：**出处、硬件/版本上下文、具体技术点、如何对照排查**。其后 **附录** 保留可复制的通用排查模板，便于工单套用。

> 原厂闭源 BSP 的 patch 若未公开，请在内部分支建立 **「镜像案例」** 链接到本文结构，避免知识只活在口头。

## 第一部分：真实案例（有公开出处）

### 案例 A — RK806 默认 pinctrl 未应用 + `pmic_sleep1` 浮空，导致无法进入深睡（Orange Pi 官方树）

| 字段 | 内容 |
|------|------|
| **出处** | Orange Pi 官方内核 commit：[Fix some boards cannot enter deep sleep mode](https://github.com/orangepi-xunlong/linux-orangepi/commit/0d1781e72fb7707a0bbc4419c8f1bc75a113f19a)（作者 baiywt，2023-04） |
| **现象** | 部分板子 **无法进入 deep sleep**（深睡路径异常或无法保持低功耗状态）；与 PMIC 睡眠脚电平/状态机相关。 |
| **根因（补丁说明隐含）** | ① **`rk806_pinctrl_init()` 只 lookup 了 `default` state，却从未 `pinctrl_select_state(..., default)`**，导致启动后引脚实际状态可能仍非预期。② `rk3588s-pinctrl.dtsi` 里 **`pmic_sleep1`（GPIO0_A2，功能复用为 pmic_sleep1）** 原配置为 **`pcfg_pull_none`（无上下拉）**，在深睡场景下易出现 **浮空/毛刺**，与 PMIC 睡眠控制脚要求不符。 |
| **具体修改** | 1）`drivers/mfd/rk806-core.c`：在成功 lookup `default` 后增加 **`pinctrl_select_state(p, default_st)`**，失败打 `dev_err`。2）`arch/arm64/boot/dts/rockchip/rk3588s-pinctrl.dtsi`：将 `pmic_sleep1` 脚由 **`&pcfg_pull_none` 改为 `&pcfg_pull_down`**。 |
| **排查手段（可复现）** | - 用 **精密电源** 看 suspend 后电流是否 **达不到** 板级 deep sleep 目标。`-` 示波器量 **`pmic_sleep*`** 相关脚在 **suspend 前后** 电平是否稳定、是否悬空抖动。`-` 对比 **是否合入上述 commit** 的 DTS + `rk806` 驱动。 |
| **处理思路** | - **合入或 cherry-pick** 该修复；或在内部分支做 **等价修改** 并经 PMIC 同事确认 **sleep 脚电气要求**（上拉/下拉/禁止浮空）。`-` 审计其它 PMIC 睡眠脚在 **sleep pinctrl state** 与 **default state** 是否一致应用。 |
| **关联工单** | [ubuntu-rockchip #1070](https://github.com/Joshua-Riek/ubuntu-rockchip/issues/1070)（Orange Pi 5+、`systemctl suspend` 无法唤醒；报告者认为与 `rk3588s-pinctrl.dtsi` PMIC 段有关，并 **显式指向上述 orangepi commit** 作为上游修复参考）。 |

**原因小结**：PMIC **睡眠控制脚** 既是 **硬件信号完整性** 问题，也是 **驱动是否在 probe 时把 default pinctrl 真正选中** 的问题；只改 DTS 或只改驱动都可能不够，需与 **数据手册/参考设计** 对齐。

### 案例 B — 发行版整合内核：休眠后无法唤醒，维护者指向 DDR/BL31 与 BSP 版本（社区多板共性）

| 字段 | 内容 |
|------|------|
| **出处** | [ubuntu-rockchip #521 — Unable to wake after suspending](https://github.com/Joshua-Riek/ubuntu-rockchip/issues/521)（Orange Pi 5 Plus，Ubuntu 22.04 预装镜像，约 2023-12） |
| **现象** | `suspend` 后 **屏幕黑、电源键无法唤醒**，只能 **硬复位**；偶发似乎成功一次，多数失败。 |
| **维护者结论（issue 内原话要点）** | 存在 **新版 DDR 与 BL31 blob** 可修复部分 suspended 相关问题，但发行版侧 **难以单独升级**（担心与其它发行版/用户环境不兼容）；同时提到 **也可能是内核驱动**；长期依赖 **新 BSP（如 Linux 6.1 路线）** 收敛。 |
| **与案例 A 的关系** | **不同层**：#521 强调 **固件 blob + 内核整体版本**；案例 A 是 **可指到具体两行 DTS + 一段 pinctrl 初始化** 的修复。实际排障应 **并行验证**：先查 **DTS/PMIC 脚**（案例 A），再对齐 **BL31+DDR+内核** 矩阵（本案例）。 |
| **排查手段** | 记录完整 **固件包版本**；在厂商验证组合上 **交叉对比**；串口看 **最后一条内核/EL3 日志**（若可开）。 |
| **处理思路** | 使用 **厂商发布说明中的兼容组合**；若必须单独升内核，同步 **BL31/DDR init** 的 release note。 |

### 案例 C — `spi-rockchip` 系统休眠与 runtime PM 叠床架屋，二次关时钟触发 `WARN_ON`（RK3588 EVB 日志）

| 字段 | 内容 |
|------|------|
| **出处** | 内核邮件 / Patchew：[spi: rockchip: Avoid redundant clock disable in pm operation](https://patchew.org/linux/20240824051452.3954878-1-jon.lin@rock-chips.com/)（Jon Lin，Rockchip） |
| **硬件上下文** | 邮件内栈与日志标明：**Rockchip RK3588 EVB1 LP4 V10 Board (DT)**，内核约 **5.10.66**。 |
| **现象** | suspend/resume 路径上出现 **`clk_spi0 already unprepared`**，最终在 `clk_core_unprepare` 触发 **`WARN_ON`**。 |
| **根因** | 早前将 **system suspend** 挂到 **NOIRQ_SYSTEM_SLEEP_PM** 的改动，与 **runtime suspend** 已关掉时钟的路径 **重复 `clk_disable_unprepare`**：设备在 **runtime 已 suspended** 时再走 **系统 suspend**，会对 **已 unprepare 的时钟** 再 unprepare 一次。 |
| **修复要点** | 将 **关钟/开钟** 逻辑收敛到 **`runtime_suspend`/`runtime_resume`**；在 **`rockchip_spi_suspend`** 中 **仅当 `!pm_runtime_status_suspended(dev)`** 时才调用 `rockchip_spi_runtime_suspend`；`resume` 侧对称处理，并保留 **`spi_controller_suspend/resume`** 与 **pinctrl sleep/default** 顺序。 |
| **排查手段** | `dmesg` 搜索 **`already unprepared`**、`clk_core_unprepare`；确认问题 SPI 控制器是否 **同时启用 runtime PM + PM_SLEEP**。 |
| **处理思路** | 合入上游思路：**系统 PM 与 runtime PM 对时钟/复位只能有一条“实作路径”**，另一条通过 **状态判断** 避免重复操作。 |

**原因小结**：RK3588 平台外设多，**runtime PM 默认开启** 后，这类 **双重 PM** 回归会反复出现；评审时要问：**suspend 里做的事 runtime 是否已做过？**

### 案例 D — `drm/rockchip` VOP2：误用 `regcache_sync()` 做 resume，与 RK3588 内部电源域上电顺序冲突

| 字段 | 内容 |
|------|------|
| **出处** | 主线邮件列表补丁（节选标题）：[`Revert "drm/rockchip: vop2: Use regcache_sync() to fix suspend/resume"`](https://lkml.indiana.edu/2311.2/06683.html)（系列 `[PATCH v2 02/12]` 中的一环，2023-11 前后） |
| **现象** | 使用 `regcache_sync()` 在 **resume** 时把缓存寄存器推回硬件后，在 **RK3588** 上出现 **显示相关异常**（与 suspend/resume 可靠性有关；具体表现依集成版本可为黑屏、模式错误等，以补丁说明为准）。 |
| **根因（补丁说明摘要）** | RK3588 VOP2 上 **4 个 Cluster window** 以及 **Esmart1/2/3** 等寄存器，在 **内部电源域（PD）尚未上电** 时 **无法正确配置**；`regcache_sync()` 会在 **错误时机** 把缓存写穿到硬件。更合理的是在后续 **`vop2_enable()`** 路径用 **`regmap_reinit_cache()`** 等机制，与 **硬件真实上电顺序** 对齐，并避免在 `vop2_disable()` 中不当使用 `regcache_mark_dirty()`（以该系列补丁最终说明为准）。 |
| **排查手段** | 黑屏但系统存活时（SSH）对比 **合入/回退该 revert 系列**；`dmesg` 查 **vop2/drm** 报错；多测 **HDMI/DP + 多 pipe**。 |
| **处理思路** | 跟随主线 **VOP2 RK3588** 的 suspend/resume 修复系列；原厂 BSP 若 **backport 了 regcache_sync 方案**，需对照主线 **是否已 revert 并改用 reinit_cache**。 |

**原因小结**：大型显示 IP 内部有 **多级 PD**，**寄存器缓存与硬件可访问窗口** 不一致时，**“同步缓存到硬件”** 反而是 bug 来源。

### 案例 E — Mali Panthor：系统/runtime PM suspend **失败后** 设备状态机损坏，需 **硬复位 + 重载固件**

| 字段 | 内容 |
|------|------|
| **出处** | 主线补丁邮件：[drm/panthor: Reset device and load FW after failed PM suspend](https://lkml.iu.edu/2410.1/07474.html)（系列 `[PATCH 3/3]`，约 2024-10） |
| **现象** | **PM suspend 失败** 或异常返回后，GPU **后续无法再正常完成 firmware 加载/reset**，整机图形或后续 suspend 行为异常（具体依赖用户态与失败路径）。 |
| **根因类型** | **加速器类 IP**：固件运行态与 **硬件 reset 线**、**PM 状态机** 强耦合；**失败路径若未定义**，会停留在 **半初始化** 状态。 |
| **修复思路（抽象）** | 在检测到 **suspend 失败** 后，执行 **device reset** 并 **重新加载固件**，使状态机回到 **与 cold boot 后首次 init 等价** 的已知点。 |
| **对 RK3588 的映射** | RK3588 若使用 **Mali 新栈（Panthor）** 或同类 **FW 型 GPU/NPU**，原厂应检查 **自家 BSP 是否在 failed suspend 路径有等价恢复**；不能假设 “失败后下次自动好”。排查时抓 **`dmesg` Panthor/Mali**、`runtime_status`、用户态是否 **卡 job**。 |

> 注：此条 **上游补丁针对 Panthor**；Rockchip BSP 可能仍用 **panfrost/厂商私有栈**，但 **「失败需 reset+重载 FW」** 的模式仍可直接套到 **NPU/多媒体固件** 评审清单。

### 案例 F — Fedora 上 RK3588（Orange Pi 5 Max）：suspend 后唤醒像 **冷启动**

| 字段 | 内容 |
|------|------|
| **出处** | Fedora 讨论帖：[Arm64 & rk3588: suspend does not work](https://discussion.fedoraproject.org/t/arm64-rk3588-suspend-does-not-work/171095) |
| **现象** | 进入 suspend 后 LED 等状态像睡眠，但 **键鼠无法唤醒**；按机身键后 **像重新开机** 而非 resume（用户侧描述为 **非恢复式启动**）。 |
| **技术分析空间** | 帖内更像 **发行版/内核/设备树/固件组合** 的综合问题，**未收敛到单条 commit**；贡献者建议用 **Fedora build 二分** 定位回归。 |
| **对负责人的价值** | 提醒：**同一颗 RK3588**，在 **Fedora vs 厂商 BSP** 上 suspend 表现可完全不同；给客户排障时要先 **锁定软件栈与 DT 来源**，避免把 **BSP 已修** 的问题在 **社区内核** 上重复定性为 “芯片 bug”。 |

## 第二部分：快速对照表（真实案例 → 你第一步看什么）

| 案例 | 第一层证据 | 第二层验证 |
|------|------------|------------|
| A RK806/pinctrl | 板子是否用 **RK806**；`rk3588s-pinctrl.dtsi` 里 **`pmic_sleep1` 上下拉** | `rk806` 驱动是否在 init 里 **`pinctrl_select_state(default)`** |
| B 固件/整合内核 | 是否 **非厂商验证组合**；issue 描述与 **#521** 类似 | 对齐 **BL31+DDR blob+内核** 矩阵 |
| C SPI 双 PM | `dmesg` **`already unprepared`** | `spi-rockchip` **suspend vs runtime** 是否重复关钟 |
| D VOP2 缓存 | **显示 resume** 异常且与 **VOP2** 版本相关 | 是否误用 **`regcache_sync`** 于 **PD 未就绪** 阶段 |
| E FW 加速器 | **`failed to suspend`** 后 GPU/NPU **永久异常** | 失败路径是否有 **reset+reload fw** |
| F 发行版 | **Fedora/Arch 等** 非 BSP | 先 **换厂商镜像 A/B**，再谈芯片 |

## 附录 A：通用排查模板（无公开出处时的工单骨架）

当 **尚无** 可引用 commit 时，仍建议工单包含：

1. **板型 / DRAM / PMIC 型号 / 内核 commit / BL31+DDR 版本**  
2. **串口最后一行** + **suspend 前后电流**  
3. **`/sys/kernel/debug/wakeup_sources` 快照**（若可用）  
4. **最小 rootfs + 模块黑名单** 二分结果  
5. **结论分类**：硬件脚、DTS、驱动、固件、发行版配置  

更细的命令与仪器说明见：[09_现场测量与日志方法论_zh.md](09_现场测量与日志方法论_zh.md)。
