## Q1：Linux 中断处理的完整路径——从硬件触发到驱动 handler 执行

### 背景知识

中断是外设与 CPU 之间的异步通信机制。理解完整中断路径是编写可靠驱动的前提。以 ARM + GICv2 为例，一次中断从硬件触发到驱动 handler 完成执行，至少经过 **7 个阶段**。

```
完整中断路径（ARM + GICv2）：

  外设                GIC                       CPU                     Linux 内核
  ────                ───                       ───                     ──────────
    │                  │                         │                         │
    │ ① 拉高 IRQ 线   │                         │                         │
    │────────────────→ │                         │                         │
    │                  │ ② 设置 pending 位       │                         │
    │                  │    检查 priority/mask   │                         │
    │                  │ ③ 向目标 CPU 发信号     │                         │
    │                  │────────────────────────→│                         │
    │                  │                         │ ④ CPU 跳转异常向量表    │
    │                  │                         │    保存上下文(pt_regs)  │
    │                  │                         │────────────────────────→│
    │                  │                         │                         │ ⑤ gic_handle_irq()
    │                  │                         │                         │    读 GICC_IAR 获取 hwirq
    │                  │                         │                         │ ⑥ irq_domain 翻译
    │                  │                         │                         │    hwirq → Linux virq
    │                  │                         │                         │ ⑦ generic_handle_irq()
    │                  │                         │                         │    → 驱动 handler
    │                  │                         │                         │ ⑧ 写 GICC_EOIR (EOI)
    │                  │                         │ ← 恢复上下文，返回     │
```

### 答题要点

1. **外设拉高 IRQ 线**：外设在特定事件发生时（如 DMA 完成、FIFO 达到阈值），通过硬件线或 MSI 消息向中断控制器发出中断请求。
2. **GIC 记录 pending 并仲裁**：GIC Distributor（GICD）在 `GICD_ISPENDRn` 中设置对应中断号的 pending 位，同时根据优先级（`GICD_IPRIORITYRn`）和目标 CPU 亲和性（`GICD_ITARGETSRn`）选择把中断转发给哪个 CPU Interface。
3. **CPU 跳转到异常向量表**：CPU 的 IRQ 异常入口在 ARM64 中位于 `arch/arm64/kernel/entry.S` 的 `vectors` 表。CPU 自动完成的硬件动作：保存 PSTATE 到 SPSR\_EL1、保存返回地址到 ELR\_EL1、切换到 EL1 的 SP（SP\_EL1）。

   **补充：安全世界是否有单独的向量表？能处理“特殊中断”吗？**
   - ARMv8 每个异常级都有自己的向量基址寄存器：EL1 用 `VBAR_EL1`，EL2 用 `VBAR_EL2`，EL3 用 `VBAR_EL3`。因此 Secure Monitor/安全固件确实有自己独立的向量表（例如 TF-A 在 EL3 设置 `VBAR_EL3`）。
   - GIC 的中断分组（Group 0 / Group 1S / Group 1NS）以及路由配置决定中断进入哪个世界/异常级。常见配置是：Secure 中断路由到 EL3（或 Secure EL1）由固件/安全 OS 处理；Linux 运行在 Non-secure EL1，主要处理 Group 1NS。
   - “特殊中断”的常见形态是 FIQ 被配置为进入 EL3（安全计时器、策略类看门狗、TrustZone 服务等）。Linux 一般不会直接处理这类 secure 中断，而是由固件先处理，再决定是否通知非安全世界。
4. **`gic_handle_irq()`** **读取硬件中断号**：读 `GICC_IAR` 寄存器获取当前最高优先级的 pending 中断号（hwirq），同时 GIC 自动将该中断状态从 pending 变为 active。
   ```
   内核源码路径：drivers/irqchip/irq-gic.c → gic_handle_irq()
                 drivers/irqchip/irq-gic-v3.c → gic_handle_irq()（GICv3）
   ```
   **补充：`GICC_IAR`** **这个“地址”从哪来？是不是写进了某个寄存器？**
   - GICv2 的 CPU Interface（GICC）是内存映射寄存器（MMIO）。CPU 对一段固定的物理地址范围做 load/store，硬件把这些访问解释为“读写寄存器”，不需要也不存在“把地址写进寄存器”的步骤。
   - Linux 在启动/探测阶段通过设备树/ACPI 获得 GIC 的 `reg` 资源（GICD/GICC 的物理基址），再 `ioremap` 成内核虚拟地址，保存在 irqchip 驱动私有结构中。读 `GICC_IAR` 实际就是 `readl_relaxed(gicc_base + GICC_IAR)`。
   - GICv3 的 CPU 接口改为系统寄存器（例如 `ICC_IAR1_EL1` / `ICC_EOIR1_EL1`），因此不再依赖 GICC 的 MMIO 基址。
5. **`irq_domain`** **翻译**：将 GIC 的硬件中断号（hwirq）翻译为 Linux 虚拟中断号（virq）。这一步由 `irq_find_mapping()` 完成。

   **补充：`irq_find_mapping()`** **是怎么“找”的？**
   - `irq_domain` 可以理解为“某个中断控制器的编号空间（hwirq）”到“Linux 全局 IRQ 编号空间（virq）”的一张映射表。
   - 映射通常在设备树解析阶段创建：`of_irq_get()`/`irq_of_parse_and_map()` → `irq_create_of_mapping()` → `irq_domain_create_mapping()`，此时 domain 内会建立 `hwirq -> virq` 的反向索引（revmap）。
   - 中断发生时，`irq_find_mapping(domain, hwirq)` 通过 revmap（可能是线性数组或基于树的稀疏映射结构）快速查到对应的 `virq`。如果找不到，往往意味着设备树描述或驱动初始化阶段没有为该 hwirq 建立映射。
6. **`generic_handle_irq(virq)`**：根据 virq 查找 `irq_desc` 结构，执行其中的 `handle_irq` 回调（通常是 `handle_fasteoi_irq` 或 `handle_level_irq`），最终调用驱动通过 `request_irq` 注册的 handler。

   **补充：从** **`virq`** **到驱动 handler 的关键调用链（概念版）**
   ```
   gic_handle_irq()
     -> __handle_domain_irq(domain, hwirq, regs)
        -> generic_handle_irq(virq)
           -> handle_irq_desc(desc)
              -> desc->handle_irq(desc)           // flow handler：level/edge/fasteoi/...
                 -> handle_irq_event(desc)        // 遍历 action 链（共享 IRQ 时可能多个）
                    -> action->handler(irq, dev_id)
                 -> irqchip 的 eoi/unmask 等动作  // 由 flow handler 选择合适时机执行
   ```
   - `irq_desc` 是“这个 virq 的内核侧状态机”，包含 `irq_data`（指向底层 irqchip）、驱动注册的 `action` 链、统计计数、屏蔽深度等。
   - 对 GIC 这类 EOI/Deactivate 模型的控制器，常见 flow handler 是 `handle_fasteoi_irq`：它会在合适的时机完成 EOI，并配合 mask/unmask 避免电平中断因“未清源”导致重入。
7. **写 GICC\_EOIR（End of Interrupt）**：handler 返回后，内核向 GIC 写 EOI，告诉 GIC 该中断处理完毕，GIC 将中断状态从 active 变为 inactive，允许下一次同类中断触发。  

### 深入追问

**Q：GICv2 和 GICv3 在中断处理路径上有什么关键区别？**

| 特性        | GICv2                       | GICv3                       |
| --------- | --------------------------- | --------------------------- |
| 架构        | GICD + GICC (MMIO)          | GICD + GICR + ICC (系统寄存器)   |
| CPU 接口访问  | MMIO (`readl`/`writel`)     | 系统寄存器 (`ICC_IAR1_EL1`)      |
| 支持 CPU 核数 | 最多 8 核                      | 无限制                         |
| 中断号范围     | 最多 1020 个                   | LPI 扩展到数万个                  |
| 亲和性路由     | `GICD_ITARGETSRn`（8-bit 位图） | `GICD_IROUTERn`（Affinity 值） |
| EOI 模式    | GICC\_EOIR (MMIO)           | `ICC_EOIR1_EL1` (系统寄存器)     |

GICv3 的 CPU 接口通过系统寄存器访问，不再走 MMIO 总线，减少了一次总线事务的延迟（约 20-50ns），在高频中断场景下性能提升明显。

**补充：一个更贴近工程的对比例子（为什么 sysreg 会更快）**

假设某外设在“未充分合并中断/批处理”的情况下中断频率达到 200k～500k 次/秒。以 GICv2 为例，每次中断入口至少包含：

- 读一次 `GICC_IAR`（MMIO read）
- 写一次 `GICC_EOIR`（MMIO write）

当中断频率为 400k 次/秒时，仅 CPU 接口的读写就会产生约 800k 次 MMIO 事务。对于很多 SoC，这些事务会经过互连仲裁与外设桥，带来可见的固定开销，并可能影响其它 master 的时延。GICv3 把这两步变成系统寄存器访问后，通常能显著降低中断入口/出口的固定成本，并减少互连压力。

**两种情况下“处理上需要有什么区别”？**

- 对普通设备驱动：几乎没有区别。驱动只看到 `virq` 与 `request_irq/request_threaded_irq` 的统一语义，底层是 GICv2 还是 GICv3 对驱动透明。
- 对 irqchip 驱动/低层调试：有区别。GICv2 可用 MMIO 直读寄存器定位；GICv3 的 CPU 接口主要通过系统寄存器与内核 debug 信息定位，并且引入 Redistributor、`GICD_IROUTERn`、LPI/ITS 等更复杂的路由与分发语义。

**Q：读 GICC\_IAR 和写 GICC\_EOIR 之间发生了什么？如果 handler 很慢会怎样？**

从读 IAR 到写 EOIR 这段时间，中断在 GIC 中处于 **active** 状态。此时：

- 同一中断号的新请求会被 GIC 记为 active+pending，但不会再次发信号给 CPU
- 如果 handler 执行时间过长（比如错误地在 hardirq 中做了耗时操作），会导致：
  - 其他中断被延迟处理（hardirq 上下文默认关中断或关抢占）
  - 看门狗超时触发系统复位
  - 实时性严重下降

这也是为什么内核强调 hardirq handler 要尽可能短——只做必要的硬件交互，将真正的处理逻辑推迟到下半部。

**Q：异常向量表的具体布局是什么样的？**

ARM64 的异常向量表定义在 `arch/arm64/kernel/entry.S`：

```
偏移量      异常来源             异常类型
──────      ────────             ────────
0x000       当前 EL, SP_EL0     Synchronous
0x080       当前 EL, SP_EL0     IRQ
0x100       当前 EL, SP_EL0     FIQ
0x180       当前 EL, SP_EL0     SError

0x200       当前 EL, SP_ELx     Synchronous
0x280       当前 EL, SP_ELx     IRQ          ← Linux 内核中断入口
0x300       当前 EL, SP_ELx     FIQ
0x380       当前 EL, SP_ELx     SError

0x400       低 EL, AArch64      Synchronous  ← 用户态系统调用入口
0x480       低 EL, AArch64      IRQ          ← 用户态被中断打断
0x500       低 EL, AArch64      FIQ
0x580       低 EL, AArch64      SError

0x600       低 EL, AArch32      Synchronous
0x680       低 EL, AArch32      IRQ
...
```

Linux 内核运行在 EL1、使用 SP\_EL1，所以内核态被 IRQ 打断时跳转到偏移 `0x280` 处。

### 代码示例

下面的代码展示了在驱动中完整的中断注册与处理过程：

```c
#include <linux/interrupt.h>
#include <linux/platform_device.h>

struct my_device {
    void __iomem *regs;
    int irq;
    u32 event_status;
};

/* hardirq handler —— 在中断上下文执行，关中断/关抢占 */
static irqreturn_t my_irq_handler(int irq, void *dev_id)
{
    struct my_device *mydev = dev_id;

    /* 读取硬件状态寄存器，确认是否是本设备产生的中断 */
    u32 status = readl(mydev->regs + REG_IRQ_STATUS);
    if (!(status & IRQ_PENDING_MASK))
        return IRQ_NONE;  /* 不是我的中断（共享 IRQ 场景） */

    /* 清除硬件中断标志 —— 必须在 handler 中完成 */
    writel(status, mydev->regs + REG_IRQ_CLEAR);

    /* 保存状态供下半部使用 */
    mydev->event_status = status;

    return IRQ_WAKE_THREAD;  /* 唤醒线程化下半部 */
}

/* 线程化下半部 —— 在内核线程上下文执行，可以睡眠 */
static irqreturn_t my_irq_thread(int irq, void *dev_id)
{
    struct my_device *mydev = dev_id;

    if (mydev->event_status & EVENT_DMA_DONE)
        complete(&mydev->dma_completion);

    if (mydev->event_status & EVENT_ERROR)
        dev_err(mydev->dev, "硬件错误: status=0x%08x\n", mydev->event_status);

    return IRQ_HANDLED;
}

static int my_probe(struct platform_device *pdev)
{
    struct my_device *mydev;
    int ret;

    mydev = devm_kzalloc(&pdev->dev, sizeof(*mydev), GFP_KERNEL);
    if (!mydev)
        return -ENOMEM;

    mydev->regs = devm_platform_ioremap_resource(pdev, 0);
    if (IS_ERR(mydev->regs))
        return PTR_ERR(mydev->regs);

    /* 从设备树获取中断号（已经是翻译后的 Linux virq） */
    mydev->irq = platform_get_irq(pdev, 0);
    if (mydev->irq < 0)
        return mydev->irq;

    /* 注册线程化中断 —— 推荐方式 */
    ret = devm_request_threaded_irq(&pdev->dev, mydev->irq,
                                     my_irq_handler,   /* hardirq 上半部 */
                                     my_irq_thread,     /* 线程化下半部 */
                                     IRQF_ONESHOT,      /* handler 返回前不重新使能中断 */
                                     "my_device",
                                     mydev);             /* dev_id: 传给 handler 的参数 */
    if (ret) {
        dev_err(&pdev->dev, "中断注册失败: %d\n", ret);
        return ret;
    }

    return 0;
}
```

**补充：`request_irq/request_threaded_irq`** **的 flags 常用取值与含义**

| flags                                  | 含义                                    | 典型使用场景                                                         |
| -------------------------------------- | ------------------------------------- | -------------------------------------------------------------- |
| `IRQF_TRIGGER_RISING/FALLING/HIGH/LOW` | 指定触发方式（边沿/电平）                         | 平台未在设备树/固件中固定触发方式，或需要显式约束；优先以设备树为准                             |
| `IRQF_SHARED`                          | 允许多个设备共享同一个 IRQ 线                     | PCI INTx、某些 SoC 的共享中断线；要求 handler 能返回 `IRQ_NONE` 且 `dev_id` 非空 |
| `IRQF_ONESHOT`                         | threaded handler 结束前保持中断线被 mask（防止重入） | 上半部不清源、清中断需要睡眠（I2C/SPI）或电平中断易重入的场景                             |
| `IRQF_NO_SUSPEND`                      | 系统 suspend 时仍保持该中断可用                  | 作为唤醒源或必须在 suspend 期间响应的中断（需谨慎，可能影响低功耗）                         |
| `IRQF_PERCPU`                          | 每 CPU 一个独立中断源/handler                 | 本地计时器、IPI 类中断等（通常是架构/核心子系统使用）                                  |
| `IRQF_NO_THREAD`                       | 禁止该中断被线程化                             | 极少数对时延/上下文有严格要求的中断（常由内核/架构代码使用）                                |

### 实战陷阱

1. **中断注册成功但 handler 从未被调用**

   这是最常见的中断问题。故障现象：`/proc/interrupts` 中对应中断行的计数始终为 0。

   **排查过程：**
   ```bash
   # 步骤 1：确认中断是否在 /proc/interrupts 中注册
   cat /proc/interrupts | grep my_device
   # 如果看不到 my_device 行，说明 request_irq 失败或未执行

   # 步骤 2：确认硬件中断号是否正确
   cat /sys/kernel/debug/irq/irqs/IRQ_NUMBER   # 查看 irq_desc 详情

   # 步骤 3：检查 GIC 配置
   # 在 devmem2 或 JTAG 下检查 GICD 寄存器：
   devmem2 0x01001100 w  # GICD_ISENABLERn：对应位是否为 1（中断已使能）
   devmem2 0x01001200 w  # GICD_ISPENDRn：对应位是否有 pending（硬件有没有触发）
   devmem2 0x01001800 w  # GICD_ITARGETSRn：目标 CPU 是否正确
   ```
   **常见原因清单：**
   | 原因                      | 症状                                     | 修复                                                                                                                                           |
   | ----------------------- | -------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------- |
   | 设备树中断号写错（off-by-one）    | `GICD_ISPENDRn` 有 pending 但 Linux 侧没响应 | 检查设备树 `interrupts` 属性。很多芯片手册把 SPI 用“GIC 全局中断 ID”（从 32 开始）标号，但设备树里 `<GIC_SPI X ...>` 的 `X` 通常是 SPI 索引（从 0 开始）。若手册写 ID=89，则设备树常见要写 `89-32=57`。 |
   | 触发方式不匹配                 | 边沿触发但线是电平信号                            | 检查 `GICD_ICFGRn` 配置                                                                                                                          |
   | 中断被 ATF 划入 Secure Group | `GICD_IGROUPRn` 对应位为 0                 | 联系安全团队修改 ATF 配置                                                                                                                              |
   | 外设时钟未使能                 | 外设本身不工作                                | 检查 `clk_prepare_enable` 是否调用                                                                                                                 |
   | 外设中断 mask 寄存器未配置        | 外设内部屏蔽了中断输出                            | 检查外设数据手册的中断使能位                                                                                                                               |
2. **EOI/Deactivate 语义配置错误导致“中断处理一段时间后彻底不再来”**

   在 GICv2 的 priority drop + deactivation 分离模式下（`GICC_CTLR.EOImodeNS = 1`），如果驱动没有正确写 `GICC_DIR`（Deactivate Interrupt Register），中断会一直保持 active 状态，后续同一中断号的请求永远不会被 forward 给 CPU。

   **故障现象**：设备正常工作了一段时间后突然"死了"——不再产生中断。`/proc/interrupts` 计数停止增长，但外设状态寄存器显示有待处理事件。

   **一个典型“踩坑用例”**：
   - 厂商 BSP 为了做“更严格的优先级控制”开启了 `EOImodeNS=1`（EOI 只做 priority drop，deactivate 需要写 `GICC_DIR`）。
   - 同时对 irqchip 做了裁剪/移植，结果 EOI 路径里只写了 `GICC_EOIR`，遗漏了 `GICC_DIR`。
   - 系统运行初期看似正常，但当“active 期间再次触发”（active+pending）叠加后，active 位长期不被清，最终表现为该中断永远不再 forward。
   **排查方法**：
   ```bash
   # 通过 JTAG 或 devmem 读 GICD_ISACTIVERn，检查中断是否卡在 active 状态
   devmem2 0x01001300 w   # GICD_ISACTIVERn
   # 如果对应位为 1，说明中断仍在 active 状态——EOI 未正确完成
   ```
   **修复要点**：
   - 不要在外设驱动里“手搓”GIC 寄存器；让内核 irqchip 完成 EOI/Deactivate。
   - 如果必须改动 `EOImodeNS`，确保 EOI 路径匹配：要么使用 combined EOI（EOI 同时 deactive），要么补齐 `GICC_DIR` 写入。

## Q2：上半部和下半部的区别？有哪些下半部机制？

### 背景知识

Linux 将中断处理分为两个阶段：**上半部（Top Half / hardirq）** 和 **下半部（Bottom Half）**。这种设计的核心目的是最小化中断关闭时间，避免系统响应性下降。

```
时间线：
 ─────────────────────────────────────────────────────────────────→
 │                │                               │
 │ 硬件中断触发    │ 上半部执行完成                  │ 下半部执行完成
 │                │ (关中断/关抢占,                  │ (开中断, 可被
 │                │  几微秒内完成)                   │  抢占或睡眠)
 │                │                               │
 │←── 上半部 ────→│←──────── 下半部 ──────────────→│
 │  hardirq ctx   │  softirq / tasklet /           │
 │  不可睡眠      │  workqueue / threaded irq      │
```

### 答题要点

**上半部（hardirq context）的职责：**

- 读取硬件状态寄存器，确定中断来源
- 清除硬件中断标志位（对电平触发中断尤其重要——不清会锁死）
- 保存必要的状态数据供下半部使用
- 调度下半部执行
- 返回 `IRQ_HANDLED` 或 `IRQ_WAKE_THREAD`

**上半部的约束：**

- 不能睡眠（不能调用 `mutex_lock`、`msleep`、`kmalloc(GFP_KERNEL)` 等）
- 不能做耗时操作（应控制在 **微秒级**）
- 在某些架构上本地中断是关闭的（ARM64 的 `PSTATE.I = 1`）

**四种下半部机制对比：**

| 机制           | 执行上下文           | 可否睡眠  | 并发控制             | 适用场景                |
| ------------ | --------------- | ----- | ---------------- | ------------------- |
| softirq      | 中断退出时/ksoftirqd | 不可    | 同类型可在不同 CPU 并发   | 网络协议栈、块设备层（高吞吐）     |
| tasklet      | 基于 softirq      | 不可    | 同一 tasklet 串行    | 简单的不需要睡眠的延迟处理       |
| workqueue    | 内核线程 (kworker)  | **可** | 取决于 workqueue 类型 | 需要睡眠的工作（I2C/SPI 读写） |
| threaded IRQ | 专属内核线程          | **可** | 每个中断号一个线程        | **推荐的通用方案**         |

**选择原则：**

- 能用 `threaded IRQ` 就用——它将大部分处理逻辑放在可调度的内核线程中，兼顾实时性和简洁性
- 需要极高吞吐量（每秒数十万次中断）才考虑 softirq
- tasklet 在新代码中已不推荐使用（社区趋势是逐步淘汰），更倾向用 workqueue 或 threaded IRQ
- 需要睡眠但不适合 threaded IRQ 的场景（如定时批处理）用 workqueue

**补充：为什么 tasklet 趋势上在被淘汰？**

- 语义尴尬：本质是 softirq 的封装，仍然在“不可睡眠”的上下文运行，容易被误用来做复杂工作，最终变成隐蔽的延迟源。
- 可维护性差：tasklet 缺少明确的线程身份与调度属性，和锁/优先级/亲和性组合时比 workqueue 更难推理。
- RT/可预测性诉求：社区更希望把延迟工作统一到 workqueue/threaded IRQ 这类进程上下文，便于控制优先级与避免长时间占用中断上下文。

**补充：哪些场景更适合 workqueue？**

- 需要睡眠的慢总线访问：I2C/SPI/MDIO 读写、固件下载、寄存器批量 dump。
- 需要合并/批处理的工作：把短时间内多次中断合并为一次处理（`mod_delayed_work()`）、周期性健康检查、后台校准。
- 需要较复杂锁与框架调用：拿 mutex、等待 completion、调用可能阻塞的子系统 API（例如 regmap cache sync）。

### 深入追问

**Q：softirq 和 tasklet 的具体执行时机是什么？**

softirq 在以下时机被检查和执行：

1. 硬件中断 handler 返回时（`irq_exit()` → `__do_softirq()`）
2. 代码显式调用 `local_bh_enable()` 时
3. `ksoftirqd` 内核线程被唤醒时（当 softirq 积压过多）

```
内核源码调用链：
irq_exit()
  → __irq_exit_rcu()
    → invoke_softirq()
      → __do_softirq()        /* 如果有 pending 的 softirq */
        → h->action(h)        /* 执行 softirq handler */

源码路径：kernel/softirq.c
```

tasklet 本质上是建立在 `TASKLET_SOFTIRQ` 和 `HI_SOFTIRQ` 之上的封装，所以它的执行时机和 softirq 一样。区别在于：同一个 tasklet 实例不会在多个 CPU 上并发执行（通过 `TASKLET_STATE_RUN` 标志位实现）。

**Q：threaded IRQ 的线程优先级是什么？在 PREEMPT\_RT 下有什么变化？**

默认情况下，threaded IRQ 线程的调度策略为 `SCHED_FIFO`，优先级为 50。可通过 `chrt` 命令或 `irq/xxx-yyy` 线程的 sched 属性调整：

```bash
# 查看中断线程的优先级
ps -eo pid,cls,rtprio,comm | grep irq/

# 调整中断线程优先级
chrt -f -p 90 <pid_of_irq_thread>
```

在 `PREEMPT_RT`（实时内核）补丁下，**几乎所有中断都被强制线程化**。原先在 hardirq context 执行的 handler 也会被放到线程中。这使得中断处理可以被更高优先级的实时任务抢占，极大提高了系统的确定性延迟（deterministic latency）。

**补充：PREEMPT\_RT 的“中断线程化”到底做了什么？**

- 核心思想：把“硬中断里做事”变成“唤醒一个可调度的内核线程做事”，让实时任务通过调度优先级获得可控的抢占关系。
- 结果表现：hardirq 里通常只做最小化的 ack/唤醒动作，真正的 handler 在 `irq/<n>-<name>` 线程里跑；系统的 worst-case latency 明显收敛。
- 边界条件：并非所有中断都能线程化。少数关键中断（例如本地定时器、部分 IPI、架构关键异常路径）会标记 `IRQF_NO_THREAD` 或走特殊路径，仍在 hardirq 里完成最小工作。

**对非实时内核的借鉴**

- 即便不打 RT 补丁，驱动也可以主动采用 `request_threaded_irq()`：把耗时/需要睡眠的逻辑挪到线程中，减少 hardirq 占用时间，降低系统抖动与看门狗风险。
- 延迟敏感但不是强实时的系统里，常见组合是：threaded IRQ + 合理的 IRQ affinity + 负载隔离（把关键中断绑到指定 CPU）。

**Q：如何判断当前代码运行在哪种上下文中？**

```c
/* 内核提供的上下文检测宏 */
in_irq()          /* 是否在 hardirq context（真正的中断处理中） */
in_softirq()      /* 是否在 softirq context（包括 BH 禁用） */
in_interrupt()    /* 是否在中断上下文（hardirq 或 softirq） */
in_task()         /* 是否在进程上下文（可以睡眠） */
in_serving_softirq()  /* 是否正在执行 softirq handler */

/* 内核源码定义：include/linux/preempt.h */
#define in_irq()           (hardirq_count())
#define in_softirq()       (softirq_count())
#define in_interrupt()     (irq_count())     /* hardirq_count() | softirq_count() */
#define in_task()          (!(in_interrupt()))
```

### 代码示例

以下展示四种下半部机制的完整用法对比：

```c
/* ==================== 方案 1: tasklet ==================== */
static struct tasklet_struct my_tasklet;
static u32 saved_status;

static void my_tasklet_func(unsigned long data)
{
    /* tasklet 上下文：不可睡眠，但中断已重新打开 */
    struct my_device *dev = (struct my_device *)data;
    process_event(dev, saved_status);
}

static irqreturn_t my_hardirq_tasklet(int irq, void *dev_id)
{
    saved_status = readl(dev->regs + STATUS_REG);
    writel(saved_status, dev->regs + CLEAR_REG);
    tasklet_schedule(&my_tasklet);
    return IRQ_HANDLED;
}

/* 初始化时 */
tasklet_init(&my_tasklet, my_tasklet_func, (unsigned long)mydev);


/* ==================== 方案 2: workqueue ==================== */
static void my_work_func(struct work_struct *work)
{
    struct my_device *dev = container_of(work, struct my_device, irq_work);

    /* 进程上下文：可以睡眠，可以调用 I2C/SPI 传输 */
    mutex_lock(&dev->lock);
    i2c_smbus_read_byte_data(dev->client, REG_DETAIL);
    mutex_unlock(&dev->lock);
}

static irqreturn_t my_hardirq_wq(int irq, void *dev_id)
{
    struct my_device *dev = dev_id;
    u32 status = readl(dev->regs + STATUS_REG);
    writel(status, dev->regs + CLEAR_REG);
    schedule_work(&dev->irq_work);
    return IRQ_HANDLED;
}


/* ==================== 方案 3: threaded IRQ（推荐）==================== */
static irqreturn_t my_hardirq(int irq, void *dev_id)
{
    struct my_device *dev = dev_id;
    u32 status = readl(dev->regs + STATUS_REG);
    if (!status)
        return IRQ_NONE;
    writel(status, dev->regs + CLEAR_REG);
    dev->pending_status = status;
    return IRQ_WAKE_THREAD;
}

static irqreturn_t my_thread_fn(int irq, void *dev_id)
{
    struct my_device *dev = dev_id;

    /* 线程上下文：可以睡眠、可以获取 mutex */
    if (dev->pending_status & BIT(0)) {
        mutex_lock(&dev->data_lock);
        spi_read(dev->spi, dev->buf, 256);
        mutex_unlock(&dev->data_lock);
    }
    return IRQ_HANDLED;
}

/* 注册 */
devm_request_threaded_irq(dev, irq, my_hardirq, my_thread_fn,
                           IRQF_ONESHOT, "my_dev", mydev);


/* ==================== 方案 4: softirq（仅内核子系统使用）==================== */
/* softirq 不暴露给驱动模块，只能在内核核心代码中定义 */
/* 以网络子系统为例：net/core/dev.c */
/* open_softirq(NET_RX_SOFTIRQ, net_rx_action); */
```

### 实战陷阱

1. **在 hardirq handler 中调用可能睡眠的函数**

   **故障现象**：内核打印 `BUG: scheduling while atomic` 后 panic。
   ```
   [   5.123456] BUG: scheduling while atomic: swapper/0/0/0x00010002
   [   5.123458] Modules linked in: my_driver(+)
   [   5.123460] CPU: 0 PID: 0 Comm: swapper/0 Not tainted 5.15.0 #1
   [   5.123465] Call trace:
   [   5.123467]  dump_backtrace+0x0/0x1c0
   [   5.123470]  show_stack+0x18/0x24
   [   5.123472]  __schedule_bug+0x64/0x80
   [   5.123475]  __schedule+0x6f0/0x920
   [   5.123478]  schedule+0x5c/0xc0
   [   5.123480]  schedule_preempt_disabled+0x14/0x20
   [   5.123483]  mutex_lock+0x30/0x50        ← 在 hardirq 中调用 mutex_lock
   [   5.123486]  my_irq_handler+0x48/0xa0 [my_driver]
   ```
   **原因分析**：`mutex_lock` 在无法获取锁时会调用 `schedule()` 进行进程切换。但 hardirq 上下文没有对应的进程可以切换（`preempt_count` 的 hardirq 位非零），触发内核检查失败。

   **修复方案**：将需要睡眠的操作移到 threaded IRQ 或 workqueue 中。如果在 hardirq 中确实需要同步，使用 `spin_lock` 替代 `mutex_lock`。
2. **workqueue 回调中处理耗时操作导致事件丢失**

   **故障现象**：高速外设（如高速 ADC）在突发模式下丢失采样数据。

   **根因**：使用系统默认 workqueue（`schedule_work`）时，多个不同设备的 work 排在同一个 kworker 线程中串行执行。如果某个 work 执行耗时较长（比如做了大量 I2C 传输），后面排队的 work 被延迟，FIFO 溢出。

   **排查步骤**：
   ```bash
   # 查看 workqueue 执行延迟
   echo 1 > /sys/kernel/debug/tracing/events/workqueue/workqueue_execute_start/enable
   echo 1 > /sys/kernel/debug/tracing/events/workqueue/workqueue_execute_end/enable
   cat /sys/kernel/debug/tracing/trace
   # 观察 work 排队到执行的时间差
   ```
   **修复方案**：为高速设备创建专用 workqueue：
   ```c
   /* 创建专用、高优先级的 workqueue */
   mydev->wq = alloc_workqueue("my_fast_wq",
                                WQ_HIGHPRI | WQ_UNBOUND, /* 高优先级、不绑定 CPU */
                                1);                       /* max_active = 1, 串行执行 */
   queue_work(mydev->wq, &mydev->irq_work);
   ```

## Q3：什么是 irq\_domain？为什么需要它？

### 背景知识

在现代 SoC 中，中断控制器往往是**层级结构**的：一个 SoC 可能有 GIC 作为主控制器，下面级联 GPIO 控制器、PCIe MSI 控制器、FPGA 中断聚合器等子控制器。每个控制器都有自己的硬件中断号空间。

`irq_domain` 就是 Linux 内核为解决**多控制器、多中断号空间**而设计的抽象层——它负责将每个控制器的\*\*硬件中断号（hwirq）\*\*翻译为全局唯一的 **Linux 虚拟中断号（virq）**。

```
                          Linux virq 空间 (全局唯一)
                       ┌─────────────────────────────┐
                       │  virq 30 ─→ GIC hwirq 62    │
                       │  virq 31 ─→ GIC hwirq 63    │
                       │  virq 32 ─→ GPIO hwirq 5    │  ← 不同 domain，hwirq 可重复
                       │  virq 33 ─→ GPIO hwirq 12   │
                       │  virq 34 ─→ FPGA hwirq 0    │
                       │  virq 35 ─→ FPGA hwirq 1    │
                       └─────────────────────────────┘

  ┌──────────────┐    ┌──────────────┐    ┌──────────────┐
  │  GIC Domain  │    │ GPIO Domain  │    │ FPGA Domain  │
  │  hwirq 0~1019│    │  hwirq 0~31  │    │  hwirq 0~15  │
  └──────────────┘    └──────────────┘    └──────────────┘
```

### 答题要点

1. **为什么需要 irq\_domain**：
   - 不同控制器的 hwirq 号可能重叠（GPIO 的 hwirq 5 和 FPGA 的 hwirq 5 是不同中断）
   - Linux 内核的 `request_irq` 等 API 使用全局唯一的 virq
   - irq\_domain 提供了 hwirq ↔ virq 的映射管理
2. **三种映射模型**：
   | 模型           | 实现            | 适用场景                       |
   | ------------ | ------------- | -------------------------- |
   | Linear（线性映射） | 数组下标索引        | hwirq 范围小且连续（GPIO、小型 FPGA） |
   | Tree（基数树映射）  | radix tree    | hwirq 范围大且稀疏（PCIe MSI）     |
   | No-map（直接映射） | hwirq == virq | 只有一个控制器且号码固定（老式 x86 PIC）   |
3. **层级 irq\_domain（hierarchy）**：
   从 Linux 3.x 开始，`irq_domain` 支持父子层级关系，完美匹配硬件上中断控制器的级联拓扑。
   ```
   级联中断控制器的 irq_domain 层级：

   ┌─────────────────────┐
   │  GIC irq_domain     │  ← root domain
   │  (parent)           │
   └─────────┬───────────┘
             │ 父子关系
   ┌─────────┴───────────┐
   │ GPIO irq_domain     │  ← child domain
   │  hwirq 0~31         │
   │  翻译: GPIO hwirq   │
   │  → GIC hwirq → virq │
   └─────────────────────┘
   ```

### 深入追问

**Q：irq\_domain 的注册和映射是在什么时候发生的？**

主要在两个阶段：

1. **中断控制器驱动初始化时**注册 irq\_domain：
   ```c
   /* 中断控制器驱动的 init 函数中 */
   domain = irq_domain_add_linear(node, nr_irqs, &my_domain_ops, priv);
   ```
2. **设备驱动调用** **`platform_get_irq()`** **时**触发映射建立：
   ```
   platform_get_irq()
     → of_irq_get()
       → irq_create_of_mapping()
         → irq_domain_alloc_irqs()         /* 层级模型 */
           → domain->ops->alloc()          /* 调用控制器驱动的 alloc 回调 */
           → irq_domain_activate_irq()     /* 配置 GIC 等硬件 */
   ```

**Q：如果驱动想手动创建 hwirq → virq 映射怎么做？**

```c
/* 对于 linear domain */
unsigned int virq = irq_create_mapping(my_domain, hwirq);
if (!virq) {
    pr_err("无法创建中断映射: hwirq=%lu\n", hwirq);
    return -ENOMEM;
}

/* 之后可以对这个 virq 调用 request_irq */
request_irq(virq, my_handler, 0, "my_dev", priv);

/* 反向查找：已知 hwirq，获取 virq */
unsigned int virq = irq_find_mapping(my_domain, hwirq);
```

**Q：层级 irq\_domain 的** **`alloc`** **回调需要做什么？**

```c
static int my_irq_domain_alloc(struct irq_domain *domain,
                                unsigned int virq, unsigned int nr_irqs,
                                void *arg)
{
    struct irq_fwspec *fwspec = arg;
    irq_hw_number_t hwirq = fwspec->param[0];
    unsigned int type = fwspec->param[1] & IRQ_TYPE_SENSE_MASK;
    struct irq_fwspec parent_fwspec;
    int i;

    for (i = 0; i < nr_irqs; i++) {
        /* 设置本级 domain 的 irq_chip 和 handler */
        irq_domain_set_hwirq_and_chip(domain, virq + i, hwirq + i,
                                       &my_irq_chip, domain->host_data);
    }

    /* 构造父 domain 的 fwspec，将 hwirq 翻译为父 domain 的 hwirq */
    parent_fwspec.fwnode = domain->parent->fwnode;
    parent_fwspec.param_count = 3;
    parent_fwspec.param[0] = GIC_SPI;
    parent_fwspec.param[1] = hwirq_to_gic_spi(hwirq);  /* 本级 hwirq → GIC SPI 号 */
    parent_fwspec.param[2] = type;

    /* 递归调用父 domain 的 alloc */
    return irq_domain_alloc_irqs_parent(domain, virq, nr_irqs, &parent_fwspec);
}
```

### 代码示例

以下是一个简化的自定义中断控制器（如 FPGA 中断聚合器）注册 irq\_domain 的完整示例：

```c
#include <linux/irqdomain.h>
#include <linux/irqchip.h>
#include <linux/of_irq.h>

struct my_intc {
    void __iomem *base;
    struct irq_domain *domain;
    int parent_irq;          /* 级联到 GIC 的那根中断线 */
    raw_spinlock_t lock;
};

/* irq_chip 回调：屏蔽/使能子中断 */
static void my_intc_mask(struct irq_data *d)
{
    struct my_intc *intc = irq_data_get_irq_chip_data(d);
    u32 mask = readl(intc->base + REG_MASK);
    mask |= BIT(d->hwirq);
    writel(mask, intc->base + REG_MASK);
}

static void my_intc_unmask(struct irq_data *d)
{
    struct my_intc *intc = irq_data_get_irq_chip_data(d);
    u32 mask = readl(intc->base + REG_MASK);
    mask &= ~BIT(d->hwirq);
    writel(mask, intc->base + REG_MASK);
}

static struct irq_chip my_irq_chip = {
    .name       = "my-intc",
    .irq_mask   = my_intc_mask,
    .irq_unmask = my_intc_unmask,
};

/* irq_domain_ops 回调 */
static int my_domain_map(struct irq_domain *d, unsigned int virq,
                          irq_hw_number_t hwirq)
{
    struct my_intc *intc = d->host_data;
    irq_set_chip_and_handler(virq, &my_irq_chip, handle_level_irq);
    irq_set_chip_data(virq, intc);
    return 0;
}

static const struct irq_domain_ops my_domain_ops = {
    .map   = my_domain_map,
    .xlate = irq_domain_xlate_twocell,  /* 设备树中用两个 cell 描述中断 */
};

/* 级联中断的 chained handler：在 GIC 的 hardirq 上下文中执行 */
static void my_intc_chained_handler(struct irq_desc *desc)
{
    struct my_intc *intc = irq_desc_get_handler_data(desc);
    struct irq_chip *chip = irq_desc_get_chip(desc);
    u32 status;

    chained_irq_enter(chip, desc);  /* 通知 GIC 进入级联处理 */

    status = readl(intc->base + REG_STATUS);
    while (status) {
        int hwirq = __ffs(status);  /* 找到最低位的 pending 中断 */
        generic_handle_domain_irq(intc->domain, hwirq);
        status &= ~BIT(hwirq);
    }

    chained_irq_exit(chip, desc);   /* 通知 GIC 退出级联处理 */
}

static int my_intc_probe(struct platform_device *pdev)
{
    struct my_intc *intc;
    struct device_node *np = pdev->dev.of_node;

    intc = devm_kzalloc(&pdev->dev, sizeof(*intc), GFP_KERNEL);
    raw_spin_lock_init(&intc->lock);

    intc->base = devm_platform_ioremap_resource(pdev, 0);

    /* 创建 linear irq_domain，支持 32 个子中断 */
    intc->domain = irq_domain_add_linear(np, 32, &my_domain_ops, intc);
    if (!intc->domain)
        return -ENOMEM;

    /* 获取级联到 GIC 的父中断 */
    intc->parent_irq = platform_get_irq(pdev, 0);

    /* 设置 chained handler —— 把父中断的处理权接管过来 */
    irq_set_chained_handler_and_data(intc->parent_irq,
                                      my_intc_chained_handler, intc);

    return 0;
}
```

### 实战陷阱

1. **irq\_domain 映射未建立导致** **`request_irq`** **失败**

   **故障现象**：设备驱动调用 `platform_get_irq()` 返回 `-EINVAL` 或 `-EPROBE_DEFER`。

   **排查过程**：
   ```bash
   # 检查设备树中中断控制器的引用关系
   dtc -I fs /sys/firmware/devicetree/base 2>/dev/null | grep -A5 "my-device"

   # 确认中断控制器驱动是否已成功加载
   ls /sys/kernel/debug/irq/domains/   # 查看已注册的 irq_domain 列表
   ```
   **常见原因**：
   - 中断控制器驱动还未 probe（加载顺序问题）→ `platform_get_irq` 返回 `-EPROBE_DEFER`
   - 设备树中 `interrupt-parent` 指向错误的节点
   - `#interrupt-cells` 数量不匹配（控制器期望 2 个 cell，设备树只写了 1 个）
2. **级联中断控制器的 chained handler 中忘记调用** **`chained_irq_enter/exit`**

   **故障现象**：级联中断控制器下的子中断第一次能正常触发，之后再也收不到。

   **根因**：`chained_irq_enter` 内部会调用 GIC 的 `irq_eoi` 回调（写 GICC\_EOIR）。如果遗漏这个调用，GIC 不会清除父中断的 active 状态，后续中断被挡在 GIC 层面。
   ```c
   /* 错误写法 —— 遗漏了 chained_irq_enter/exit */
   static void bad_chained_handler(struct irq_desc *desc)
   {
       struct my_intc *intc = irq_desc_get_handler_data(desc);
       u32 status = readl(intc->base + REG_STATUS);
       while (status) {
           generic_handle_domain_irq(intc->domain, __ffs(status));
           status &= status - 1;
       }
       /* ← 缺少 chained_irq_exit → GIC 的 EOI 未执行 → 父中断卡死 */
   }
   ```

## Q4：电平触发和边沿触发的区别与风险？

### 背景知识

中断触发方式是中断控制器的基础配置之一，直接影响中断是否能被可靠地捕获和处理。

```
电平触发（Level Triggered）：
信号 ─────┐                    ┌─────
          │  中断有效（高/低）   │
          └────────────────────┘
          ↑                    ↑
       GIC 检测到              驱动清除中断源后
       并标记 pending          信号恢复

边沿触发（Edge Triggered）：
信号 ─────┐         ┌───┐     ┌─────
          │         │   │     │
          └─────────┘   └─────┘
          ↑         ↑   ↑     ↑
        下降沿     上升沿 下降沿 上升沿
        (触发)            (触发)
```

### 答题要点

| 特性        | 电平触发                       | 边沿触发                       |
| --------- | -------------------------- | -------------------------- |
| 触发条件      | 中断信号保持有效电平期间持续触发           | 仅在信号跳变瞬间触发                 |
| 不清中断源的后果  | **死锁**：中断反复触发，CPU 无法做其他事   | 无影响，但当前事件可能未处理             |
| 丢中断风险     | 低（只要信号保持，总能检测到）            | **高**：信号跳变期间若 GIC 未采样到则丢失  |
| 共享 IRQ    | **必须用电平触发**                | 无法可靠共享                     |
| GIC 配置寄存器 | `GICD_ICFGRn` 对应位 = `0b00` | `GICD_ICFGRn` 对应位 = `0b10` |

**为什么共享 IRQ 必须用电平触发？**

因为边沿触发在 handler 执行期间，如果另一个共享该线路的设备也触发了中断，产生的第二次边沿可能已经被第一个设备的 handler 执行掩盖了（信号已经是高电平，不会有新的上升沿）。而电平触发只要信号保持有效，handler 返回后内核会再次检查中断线状态，发现仍然有效就继续处理。

### 深入追问

**Q：边沿触发丢中断的具体场景是什么？**

```
场景：外设在极短时间内连续产生两次中断

时间线：
─────────────────────────────────────────────→

外设A：  ↑ 第1次中断（上升沿）
         │
GIC：    记录 pending → 通知 CPU
         │
CPU：    │  进入 handler，读 IAR
         │    （此时中断状态：active）
         │
外设A：  │  ↑ 第2次中断（上升沿）  ← 此时 GIC 中该中断已经是 active
         │  │                        状态，新的 pending 被记录
         │  │                        为 active+pending
         │
CPU：    handler 返回，写 EOI
         │  → active+pending 变为 pending → 再次触发 → ✓ 不丢
         │
=========== 但如果时序更极端：===========

外设A：  ↑ 第1次中断（上升沿）
         │
CPU：    ↑ 正好在读 IAR 的一个时钟周期内...
         │
外设A：  ↑ 第2次中断（再次上升沿）  ← 如果 GIC 在 acknowledge 之前
         │  就已经 deassert 再 assert，取决于 GIC 实现，
         │  有可能合并为一次 pending
         │
结论：   第2次中断可能被合并，事件丢失
```

**防御措施**：在 handler 结束前**主动轮询**一次外设状态寄存器，确认没有遗漏事件：

```c
static irqreturn_t edge_safe_handler(int irq, void *dev_id)
{
    struct my_device *dev = dev_id;
    int handled = 0;

    /* 循环处理，直到外设状态寄存器显示没有 pending 事件 */
    do {
        u32 status = readl(dev->regs + STATUS_REG);
        if (!status)
            break;
        writel(status, dev->regs + CLEAR_REG);
        process_events(dev, status);
        handled = 1;
    } while (1);

    return handled ? IRQ_HANDLED : IRQ_NONE;
}
```

**Q：电平触发锁死的具体过程是什么？**

```
电平触发中断锁死流程：

  外设持续拉低 IRQ 线（活动低电平中断）
       │
       ▼
  GIC 检测到低电平 → 标记 pending → 通知 CPU
       │
       ▼
  CPU 执行 handler → 但 handler 中没有清除外设的中断源
       │                （可能是写清除寄存器地址写错了）
       ▼
  handler 返回 → EOI → GIC 解除 active
       │
       ▼
  GIC 再次检测到低电平（因为外设还在拉低 IRQ 线）
       │
       ▼
  再次标记 pending → 再次通知 CPU → 再次执行 handler
       │
       ▼
  无限循环！CPU 被完全占用处理这个中断
  → /proc/interrupts 中该中断计数疯狂增长
  → 系统卡死或看门狗超时
```

### 实战陷阱

1. **设备树触发方式与硬件实际不匹配导致的间歇性丢中断**

   **故障现象**：一个 SPI 接口的传感器芯片偶尔丢失数据就绪中断，概率约 0.1%。表现为：传感器 FIFO/状态寄存器显示“有新数据”，但驱动没进 handler，数据最终被覆盖或上层超时；在高温或高负载时丢失率显著增加。

   **现象量化（建议你在真实项目里这么做）**：
   - 对比两路计数：传感器内部“数据就绪事件计数”（如果有）/状态位翻转次数 vs `/proc/interrupts` 中该 IRQ 的计数。
   - 同时抓波形：用逻辑分析仪/示波器采集 INT 引脚 + SPI SCLK/CS，确认“INT 真的来过但 CPU 没响应”还是“INT 根本没拉到有效电平/边沿”。
   **排查过程**：
   ```bash
   # 步骤 1：对比设备树配置和芯片手册
   # 设备树写的是 IRQ_TYPE_EDGE_FALLING
   # 但查看传感器手册发现：INT 引脚为开漏输出，需要外部上拉
   # 外部上拉 + 开漏 = 电平信号，不是干净的边沿信号

   # 步骤 2：用示波器抓中断线波形
   # 发现上升沿不够陡峭（RC 时间常数太大），导致 GIC 在采样窗口内
   # 看到了多次跳变，或者根本没采样到有效边沿

   # 步骤 3：检查 GICD_ICFGRn 确认实际配置
   devmem2 0x01001C14 w   # 假设中断号落在这个寄存器范围内
   ```
   **根因拆解（为什么“低概率+受温度/负载影响”）**：
   - 开漏 + 上拉意味着 INT 本质是电平语义（通常“保持有效直到状态被读/清”）。如果误配成边沿触发，CPU 只在某一次边沿进入 handler；当边沿不够陡峭、或在中断被 mask 的窗口内发生边沿时，就可能“错过一次”。
   - 高负载时系统中断延迟增加（关中断/关抢占窗口变长），更容易把“很窄/很慢的边沿”落在不可响应的时间段；高温时漏电/阈值漂移会进一步恶化波形裕量，导致边沿采样不稳定或产生抖动。
   **修复（软件+硬件两条线）**：
   - 软件：将触发方式改为 `IRQ_TYPE_LEVEL_LOW`（或手册对应的电平类型），并确保 handler/thread\_fn 中通过 SPI 读状态/清中断源，使 INT 线真正释放。
   - 硬件：优化上拉与走线（减小 RC）、必要时加施密特触发器/电平整形，避免“慢边沿+抖动”进入 GIC。
2. **电平触发中断在 suspend/resume 后锁死系统**

   **故障现象**：系统从 suspend 唤醒后立即“卡死”，串口不断输出同一个中断 handler 的 trace，`/proc/interrupts` 中该 IRQ 计数暴增；严重时看门狗复位。

   **根因**：suspend 前外设产生了中断但未被处理（可能 suspend 流程中先关闭了 CPU 的中断响应）。Resume 后中断线仍然保持有效电平，GIC 立即触发中断，但 handler 依赖的外设时钟/电源还未恢复，无法正确读取状态寄存器来清除中断源。

   **更具体的时序（你会更容易对上现象）**：
   - suspend：设备还在拉低 IRQ（电平有效），但系统进入 suspend 流程时中断响应被关掉或 handler 不能运行。
   - resume：GIC 一恢复就立刻把该电平中断送给 CPU；但此刻外设可能仍处在断电/门控时钟状态，导致 handler 读寄存器返回全 0/总线错误，清不掉中断源。
   - 结果就是：IRQ 电平一直有效 → handler 被反复触发 → 系统被 hardirq/thread 占满。
   **修复方案**：在 suspend 回调中显式清除外设中断并 disable IRQ；并把“使能 IRQ”放在外设完全恢复之后：
   ```c
   static int my_suspend(struct device *dev)
   {
       struct my_device *mydev = dev_get_drvdata(dev);

       /* 先禁用中断，再关外设 */
       disable_irq(mydev->irq);

       /* 清除外设 pending 中断 */
       writel(0xFFFFFFFF, mydev->regs + REG_IRQ_CLEAR);

       clk_disable_unprepare(mydev->clk);
       return 0;
   }

   static int my_resume(struct device *dev)
   {
       struct my_device *mydev = dev_get_drvdata(dev);

       clk_prepare_enable(mydev->clk);

       /* 再次清除可能的 spurious 中断 */
       writel(0xFFFFFFFF, mydev->regs + REG_IRQ_CLEAR);

       enable_irq(mydev->irq);
       return 0;
   }
   ```
   **额外建议（更稳）**：
   - 若该中断是唤醒源，用 `enable_irq_wake()`/`irq_set_irq_wake()` 配合 PM 框架，而不是用 `IRQF_NO_SUSPEND` 硬扛；避免“设备未恢复但中断先跑”。
   - 把“清 pending/停设备”的动作放在更合适的 PM 阶段（例如 noirq 阶段），确保不会在 suspend/resume 的竞态窗口里留下有效电平。

## Q5：request\_irq 和 request\_threaded\_irq 的区别？IRQF\_SHARED 的约束？

### 背景知识

`request_irq` 和 `request_threaded_irq` 是 Linux 驱动注册中断处理函数的两个核心 API。理解它们的区别和使用约束，是写出健壮中断代码的前提。

```c
/* 源码位置：include/linux/interrupt.h */

/* 传统方式：handler 在 hardirq context 执行 */
static inline int __must_check
request_irq(unsigned int irq, irq_handler_t handler, unsigned long flags,
            const char *name, void *dev)
{
    /* 实际上就是 thread_fn = NULL 的 request_threaded_irq */
    return request_threaded_irq(irq, handler, NULL, flags, name, dev);
}

/* 线程化方式：handler 快速返回，thread_fn 在内核线程中执行 */
int __must_check
request_threaded_irq(unsigned int irq, irq_handler_t handler,
                     irq_handler_t thread_fn, unsigned long flags,
                     const char *name, void *dev_id);
```

### 答题要点

**`request_irq`** **vs** **`request_threaded_irq`** **核心区别：**

| 特性              | `request_irq`     | `request_threaded_irq`     |
| --------------- | ----------------- | -------------------------- |
| handler 执行上下文   | hardirq（关中断/关抢占）  | hardirq（上半部）+ 内核线程（下半部）    |
| handler 能否睡眠    | 不能                | 上半部不能，thread\_fn **可以**    |
| 内核线程            | 不创建               | 自动创建 `irq/<irq>-<name>` 线程 |
| 适用场景            | 极简 handler，纯寄存器操作 | **大多数驱动的推荐选择**             |
| PREEMPT\_RT 兼容性 | 被强制线程化            | 天然兼容                       |

**`request_threaded_irq`** **创建的内核线程：**

```bash
# 查看中断线程
ps aux | grep "irq/"

# 典型输出：
# root  45  2  0  0:00  [irq/62-my_dev]
#                        ↑    ↑    ↑
#                    前缀  virq  设备名
```

**IRQF\_SHARED 的约束（关键面试考点）：**

1. **所有共享该 IRQ 的 handler 都必须能返回** **`IRQ_NONE`**：
   - handler 被调用时，必须先检查是否是自己的设备产生的中断
   - 不是自己的中断时必须返回 `IRQ_NONE`
   - 这样内核才能把中断分发给链上的下一个 handler
   **相关故障模式（非常常见）**：
   - 共享 IRQ 上某个驱动“偷懒”不读状态寄存器，直接返回 `IRQ_HANDLED`：当另一个设备触发中断时，这个错误 handler 抢先“认领”中断，内核不会再调用后面的正确 handler；真正的中断源没清掉（电平触发），于是中断会反复触发，最终出现风暴或 `irq N: nobody cared`。
   - 共享 IRQ 上某个驱动误判条件，频繁返回 `IRQ_NONE`：会显著增加 spurious 检测命中概率，导致内核自动禁用该 IRQ（见 Q6 的 `note_interrupt` 机制）。
2. **`dev_id`** **不能为 NULL**：
   - `free_irq(irq, dev_id)` 用 `dev_id` 来确定要释放链上的哪个 handler
   - 如果 `dev_id` 为 NULL，`free_irq` 无法区分不同设备的 handler
3. **所有共享者的触发方式必须一致**：
   - 第一个注册的 handler 决定了触发方式
   - 后续注册者如果指定了不同的触发方式，会返回 `-EBUSY`
4. **共享 IRQ 必须是电平触发**（硬件约束，详见 Q4）

### 深入追问

**Q：`IRQF_ONESHOT`** **标志的作用是什么？什么时候必须用？**

`IRQF_ONESHOT` 表示在 threaded handler（`thread_fn`）执行完毕之前，不重新使能该中断。这在以下场景是**必须的**：

- 如果 hardirq handler 只返回 `IRQ_WAKE_THREAD` 而不清除硬件中断源（因为清中断需要通过 I2C/SPI 等慢速总线，不能在 hardirq 中做）
- 没有 `IRQF_ONESHOT` 时，中断在 hardirq handler 返回后就被重新使能，但此时中断源还没清除，电平触发的中断会立即再次触发，形成风暴

**补充：`IRQF_ONESHOT`** **的“重新使能”发生在什么时候、由谁做？**

- 只要一个 IRQ 被标记为 oneshot，内核中断核心会在唤醒线程化 handler 时把该 IRQ 先 mask 住（避免 thread\_fn 还没清源时再次进来）。
- 当 `thread_fn` 执行结束返回后，中断核心会在“线程收尾”阶段执行 oneshot 的 finalize 逻辑，把 IRQ unmask（恢复使能）。因此它不是驱动手动“重新使能”，而是 request\_threaded\_irq 的通用语义，由 IRQ core 自动完成。
- 你在驱动里要保证的是：thread\_fn 返回前已经把中断源清到不会继续保持有效电平；否则即使被 unmask，也会立刻再次触发。

```c
/*
 * 典型场景：I2C 接口的传感器芯片
 * 清除中断需要通过 I2C 总线读取状态寄存器
 * I2C 操作可能睡眠，不能在 hardirq 中做
 */
ret = request_threaded_irq(irq,
                            NULL,           /* 没有 hardirq handler */
                            sensor_thread_fn, /* 所有处理都在线程中 */
                            IRQF_ONESHOT | IRQF_TRIGGER_LOW,
                            "i2c-sensor",
                            sensor);
```

当 `handler` 参数传 NULL 时，内核会使用默认的 `irq_default_primary_handler`（直接返回 `IRQ_WAKE_THREAD`）。这种情况下 **必须** 指定 `IRQF_ONESHOT`，否则内核会拒绝注册并返回 `-EINVAL`。

**Q：`devm_request_irq`** **和** **`request_irq`** **有什么区别？**

`devm_request_irq` 是资源管理版本，会在设备 unbind 时自动调用 `free_irq`。好处是避免手动管理中断释放，减少资源泄漏 bug。

```c
/* 推荐使用 devm 版本 */
ret = devm_request_threaded_irq(&pdev->dev, irq,
                                 hardirq_fn, thread_fn,
                                 IRQF_ONESHOT, "my_dev", priv);
/* 无需在 remove 中调用 free_irq —— devres 自动处理 */

/*
 * 注意：devm 释放发生在 driver remove 回调之后
 * 如果 remove 中有关闭硬件的操作，而中断 handler 可能访问硬件，
 * 需要在 remove 中先手动 disable_irq 或 devm_free_irq
 */
```

### 代码示例

完整的 IRQF\_SHARED 使用示例：

```c
#include <linux/interrupt.h>
#include <linux/pci.h>

struct my_pci_device {
    void __iomem *regs;
    struct pci_dev *pdev;
};

/* 共享 IRQ 的 handler —— 必须能判断是否是自己的中断 */
static irqreturn_t my_shared_handler(int irq, void *dev_id)
{
    struct my_pci_device *mydev = dev_id;
    u32 status;

    /* 第一步：读取本设备的中断状态寄存器 */
    status = readl(mydev->regs + MY_IRQ_STATUS);

    /* 第二步：判断是否是本设备产生的中断 */
    if (!(status & MY_IRQ_PENDING)) {
        /*
         * 不是本设备的中断 —— 必须返回 IRQ_NONE
         * 这样内核会继续调用链上的下一个 handler
         */
        return IRQ_NONE;
    }

    /* 第三步：清除本设备的中断 */
    writel(status, mydev->regs + MY_IRQ_CLEAR);

    /* 第四步：处理中断 */
    handle_my_event(mydev, status);

    return IRQ_HANDLED;
}

static int my_pci_probe(struct pci_dev *pdev, const struct pci_device_id *id)
{
    struct my_pci_device *mydev;
    int ret;

    mydev = devm_kzalloc(&pdev->dev, sizeof(*mydev), GFP_KERNEL);
    mydev->pdev = pdev;

    pci_enable_device(pdev);
    mydev->regs = pci_iomap(pdev, 0, 0);

    /*
     * PCI 传统中断（INTx）是共享的，必须用 IRQF_SHARED
     * dev_id 传 mydev（非 NULL），用于 free_irq 时区分
     */
    ret = request_irq(pdev->irq, my_shared_handler,
                      IRQF_SHARED,     /* 标记为共享 */
                      "my_pci_dev",
                      mydev);          /* dev_id 不能为 NULL！ */
    if (ret) {
        dev_err(&pdev->dev, "注册共享中断失败: %d\n", ret);
        return ret;
    }

    return 0;
}

static void my_pci_remove(struct pci_dev *pdev)
{
    struct my_pci_device *mydev = pci_get_drvdata(pdev);

    /* free_irq 通过 dev_id (mydev) 定位要释放的 handler */
    free_irq(pdev->irq, mydev);
    pci_iounmap(pdev, mydev->regs);
}
```

### 实战陷阱

1. **IRQF\_SHARED 注册时 dev\_id 传了 NULL**

   **故障现象**：`request_irq` 直接返回 `-EINVAL`。
   ```
   [   3.456789] my_driver: request_irq failed: -22
   ```
   **内核源码检查点**（`kernel/irq/manage.c`）：
   ```c
   /* request_threaded_irq 中的检查 */
   if ((irqflags & IRQF_SHARED) && !dev_id) {
       /* 共享中断必须提供非 NULL 的 dev_id */
       return -EINVAL;
   }
   ```
   **修复**：传入设备私有数据结构的指针作为 `dev_id`。
2. **共享 IRQ handler 未正确返回 IRQ\_NONE 导致中断风暴**

   **故障现象**：`/proc/interrupts` 中共享中断计数暴增，系统明显变慢。

   **根因**：某个共享 IRQ 的 handler 不检查中断来源，永远返回 `IRQ_HANDLED`。当另一个共享该 IRQ 的设备触发中断时，错误 handler 先被调用并返回 `IRQ_HANDLED`，内核认为已处理完毕，不再调用链上的正确 handler。但中断源未清除（电平触发），中断立即再次触发。
   ```c
   /* 错误代码 —— 忘记检查是否是自己的中断 */
   static irqreturn_t bad_shared_handler(int irq, void *dev_id)
   {
       /* 直接处理，不检查中断来源！ */
       do_something();
       return IRQ_HANDLED;  /* ← 即使不是自己的中断也返回 HANDLED */
   }
   ```
   **一个更“像真实现场”的案例**：
   - 硬件：两张 PCIe 设备（例如网卡 + 采集卡）在某平台上走传统 INTx，并且被固件布线到同一条 IRQ 线上（共享 IRQ）。
   - 现象：采集卡在高负载下偶发丢事件，随后系统变慢；`/proc/interrupts` 里该 IRQ 计数暴涨，但采集卡的 handler 打印几乎不出现。
   - 关键线索：debugfs 显示该 IRQ 上注册了两个 handler，但 ftrace 里总是先进入网卡驱动的 handler，且它几乎每次都返回 `IRQ_HANDLED`。
   - 结论：网卡驱动没有按共享 IRQ 规则检查自身状态寄存器，错误认领了别人的中断，导致真正的中断源未清除→电平一直有效→风暴。
   - 修复：在网卡驱动 handler 中先读“中断状态/原因”寄存器，判定不是本设备就返回 `IRQ_NONE`；同时确保真正的设备在 handler/thread\_fn 中清源。
     **内核的自我保护机制**：当连续 100000 次中断中有 99900 次（99.9%）所有 handler 都返回 `IRQ_NONE`，内核会自动禁用该中断并打印警告（详见 Q6）。
3. **remove 回调中** **`free_irq`** **的 dev\_id 与注册时不一致**

   **故障现象**：`free_irq` 内核警告 `Trying to free already-free IRQ`，实际上中断并未被释放，导致卸载模块后中断 handler 指向已释放的内存——后续触发该中断时内核 oops。
   ```bash
   # 确认中断是否真的被释放了
   cat /proc/interrupts | grep my_dev
   # 如果卸载模块后仍然能看到 my_dev，说明 free_irq 没成功
   ```

## Q6：中断风暴是什么？如何检测和处理？

### 背景知识

**中断风暴（Interrupt Storm）** 是指某个中断在极短时间内被大量触发，导致 CPU 几乎全部时间都在执行中断 handler，无法调度用户进程。这通常表现为系统"假死"——键盘无响应、SSH 连接超时，但看门狗可能不触发（因为中断 handler 本身在执行）。

```
正常中断频率：
──│──────────│──────────│──────────│──→   约每 10ms 一次

中断风暴：
──│││││││││││││││││││││││││││││││││──→   每个 │ 间隔 < 1μs
  CPU 100% 时间在 hardirq context
  用户空间、内核线程完全饿死
```

### 答题要点

**中断风暴的常见原因：**

| 原因          | 说明                              |
| ----------- | ------------------------------- |
| 硬件故障        | 中断线因焊接虚焊、ESD 损坏等导致信号抖动          |
| 电平触发中断未清除   | handler 没有正确清除中断源               |
| 共享 IRQ 无人认领 | 所有 handler 返回 IRQ\_NONE，但中断线仍有效 |
| 设备固件 bug    | 外设在错误状态下持续触发中断                  |
| 触发方式配置错误    | 边沿触发配成电平触发，正常信号也被误认为中断          |

**Linux 内核的自动检测机制（`note_interrupt`）：**

内核在 `kernel/irq/spurious.c` 中实现了中断异常检测：

```
检测逻辑：
─────────────────────────────────────────────────
每次中断 handler 返回后，调用 note_interrupt():

   irq_count++

   if (handler 返回 IRQ_NONE)
       irqs_unhandled++

   if (irq_count >= 100000) {
       if (irqs_unhandled >= 99900) {
           /* 99.9% 的中断无人处理 → 判定为 spurious */
           __report_bad_irq()
           → "irq XX: nobody cared"
           → disable_irq_nosync()     /* 自动禁用该中断！ */
       }
       重置计数器
   }
─────────────────────────────────────────────────
```

### 深入追问

**Q：内核检测到中断风暴后具体会打印什么？如何阅读这段日志？**

```
[  45.123456] irq 62: nobody cared (try booting with the "irqpoll" boot parameter)
[  45.123458] CPU: 0 PID: 0 Comm: swapper/0 Not tainted 5.15.0 #1
[  45.123460] Hardware name: Vendor Board (DT)
[  45.123462] Call trace:
[  45.123465]  dump_backtrace+0x0/0x1c0
[  45.123468]  __report_bad_irq+0x3c/0xc0
[  45.123470]  note_interrupt+0x284/0x2d4
[  45.123472]  handle_irq_event_percpu+0x74/0x90
[  45.123475] handlers:
[  45.123477] [<ffffff8008123456>] my_irq_handler [my_driver] ← 注册在该 IRQ 上的 handler
[  45.123480] [<ffffff8008234567>] other_handler [other_driver]
[  45.123482] Disabling IRQ #62                               ← 内核自动禁用了该中断
```

**关键信息解读：**

- `nobody cared`：所有注册在该 IRQ 上的 handler 几乎全部返回了 IRQ\_NONE
- `handlers:` 下面列出了所有注册在该 IRQ 上的 handler 函数及所属模块
- `Disabling IRQ #62`：内核已经自动禁用了该中断——这意味着相关设备将停止工作

**Q：如何手动检测和定位中断风暴？**

```bash
# 方法 1：监控 /proc/interrupts 的变化率
watch -n 1 "cat /proc/interrupts"
# 正常中断每秒几十到几千次；如果看到某个中断每秒增长数十万以上，很可能是风暴

# 方法 2：用 perf 统计中断频率
perf stat -e irq:irq_handler_entry -a sleep 1
# 查看 1 秒内的中断总数

# 方法 3：ftrace 跟踪特定中断
echo 1 > /sys/kernel/debug/tracing/events/irq/irq_handler_entry/enable
echo "irq==62" > /sys/kernel/debug/tracing/events/irq/irq_handler_entry/filter
cat /sys/kernel/debug/tracing/trace_pipe
# 如果输出爆炸式增长，确认为中断风暴
```

**Q：内核有什么参数可以影响 spurious 中断检测行为？需要重启吗？**

```bash
# irqpoll：启用中断轮询模式，禁用的中断会通过定时器轮询处理
# 用于在中断风暴导致设备不可用时作为临时 workaround
# 这是“内核启动参数”，必须通过 bootloader 传入（例如 GRUB/U-Boot 的 bootargs）
# 生效时机：启动时解析，因此需要重启

# noirqdebug：完全关闭 spurious interrupt 检测
# 用于某些已知会误触发的硬件环境（不推荐）
# 这也是启动参数，需要重启
```

补充说明：

- `/proc/cmdline` 是只读的“本次启动命令行回显”，不能通过 `echo` 追加来改变内核行为。
- `note_interrupt` 的计数窗口/阈值（例如 100000 次、99.9%）在主线内核里通常是固定逻辑，不是一个可以在运行时自由调的 sysctl；工程上更常用的是修复根因，而不是调阈值。

### 代码示例

以下是一个驱动级别的中断风暴防护实现：

```c
#include <linux/interrupt.h>
#include <linux/jiffies.h>

struct my_device {
    void __iomem *regs;
    int irq;

    /* 中断风暴检测状态 */
    unsigned long irq_count;        /* 时间窗口内的中断计数 */
    unsigned long irq_window_start; /* 时间窗口起始时间 (jiffies) */
    bool irq_storm_detected;        /* 是否检测到风暴 */
    struct delayed_work irq_recovery_work;  /* 延迟恢复 work */
};

/* 中断风暴检测阈值 */
#define IRQ_STORM_THRESHOLD  10000   /* 每秒超过 10000 次则判定为风暴 */
#define IRQ_STORM_WINDOW_MS  1000    /* 检测时间窗口：1 秒 */
#define IRQ_RECOVERY_DELAY_MS 5000   /* 风暴后等待 5 秒再恢复 */

static irqreturn_t my_irq_handler(int irq, void *dev_id)
{
    struct my_device *dev = dev_id;
    u32 status;

    status = readl(dev->regs + STATUS_REG);
    if (!status)
        return IRQ_NONE;

    writel(status, dev->regs + CLEAR_REG);

    /* 中断风暴检测 */
    dev->irq_count++;
    if (time_after(jiffies, dev->irq_window_start +
                   msecs_to_jiffies(IRQ_STORM_WINDOW_MS))) {
        if (dev->irq_count > IRQ_STORM_THRESHOLD) {
            dev_err(dev->dev, "中断风暴！%lu 次/秒，暂时禁用中断\n",
                    dev->irq_count);
            disable_irq_nosync(dev->irq);
            dev->irq_storm_detected = true;
            /* 安排延迟恢复 */
            schedule_delayed_work(&dev->irq_recovery_work,
                                  msecs_to_jiffies(IRQ_RECOVERY_DELAY_MS));
        }
        dev->irq_count = 0;
        dev->irq_window_start = jiffies;
    }

    process_event(dev, status);
    return IRQ_HANDLED;
}

/* 风暴恢复 work：尝试重新使能中断 */
static void irq_recovery_work_fn(struct work_struct *work)
{
    struct my_device *dev = container_of(work, struct my_device,
                                         irq_recovery_work.work);

    dev_info(dev->dev, "尝试恢复中断...\n");

    /* 在恢复前重置硬件中断控制器 */
    writel(0xFFFFFFFF, dev->regs + IRQ_CLEAR_REG);
    writel(0, dev->regs + IRQ_MASK_REG);

    dev->irq_storm_detected = false;
    dev->irq_count = 0;
    dev->irq_window_start = jiffies;

    enable_irq(dev->irq);
}
```

### 实战陷阱

1. **GPIO 中断线浮空导致的随机中断风暴**

   **故障现象**：板子上电后，某个 GPIO 中断的计数在 `/proc/interrupts` 中疯涨，几秒后被内核自动禁用（`nobody cared`）。但该 GPIO 连接的外设还未上电。

   **排查过程**：
   ```bash
   # 步骤 1：确认 GPIO 中断配置
   cat /sys/kernel/debug/gpio
   # 发现该 GPIO 配置为边沿触发，但没有设置内部上下拉

   # 步骤 2：用万用表测量 GPIO 引脚电压
   # 发现电压在 0.8V~1.5V 之间浮动（VIH/VIL 不确定区域）

   # 步骤 3：在示波器上观察
   # GPIO 引脚呈现高频噪声（几 MHz），不断穿越 VIH/VIL 阈值
   # 每次穿越都产生一个边沿中断
   ```
   **修复**：在设备树中为该 GPIO 配置内部上拉/下拉：
   ```dts
   &gpio1 {
       sensor_int_pin: sensor-int-pin {
           pins = "gpio1_5";
           bias-pull-up;   /* 使能内部上拉，避免浮空 */
       };
   };
   ```
2. **PCIe 设备 INTx 中断去抖错误导致的假风暴**

   **故障现象**：某 PCIe 网卡在高流量下触发 `nobody cared`，但网卡本身没有问题。

   **根因**：该网卡使用 INTx（传统中断），与另一个 PCIe 设备共享中断线。另一个设备的驱动有 bug——它的 handler 在检查状态寄存器前做了一个 `readl` 但没有使用结果（估计是历史遗留代码），导致该 handler 总是返回 `IRQ_NONE`。网卡的正常中断被误判为 spurious。

   **排查方法**：
   ```bash
   # 查看 IRQ 62 上的所有 handler
   cat /proc/irq/62/spurious
   # count: 100032
   # unhandled: 99950
   # last_unhandled: 45123456 ms

   # 查看哪些设备共享了这个 IRQ
   cat /proc/interrupts | grep "62:"
   # 62:  100032  IR-PCI-MSI  my_netcard, buggy_device
   ```
   **修复**：升级 `buggy_device` 的驱动，或将两个设备改为 MSI 中断（每个设备独占一个中断号，不再共享）。

## Q7：设备树中如何描述级联中断控制器？

### 背景知识

现代 SoC 的中断拓扑通常是层级结构：GIC 作为根控制器，下挂 GPIO 控制器、PCIe 控制器、FPGA 中断聚合器等子控制器。设备树（Device Tree）需要准确描述这种层级关系，内核才能正确建立 irq\_domain 层级并路由中断。

```
典型 SoC 中断拓扑：

                    ┌──────────┐
                    │   GIC    │ ← root interrupt controller
                    │ (64 SPI) │
                    └────┬─────┘
                 ┌───────┼───────────┐
                 │       │           │
           ┌─────┴──┐ ┌─┴─────┐ ┌───┴────┐
           │ GPIO-A │ │GPIO-B │ │  FPGA  │ ← 子中断控制器
           │(32 irq)│ │(16irq)│ │(8 irq) │
           └───┬────┘ └───┬───┘ └───┬────┘
               │          │         │
          传感器/按键   以太网PHY   自定义逻辑
```

### 答题要点

**设备树中描述中断控制器的三个关键属性：**

| 属性                     | 作用                   | 位置         |
| ---------------------- | -------------------- | ---------- |
| `interrupt-controller` | 声明该节点是中断控制器          | 控制器节点      |
| `#interrupt-cells`     | 声明子设备描述一个中断需要几个 cell | 控制器节点      |
| `interrupt-parent`     | 指定该设备/控制器的中断父节点      | 设备节点或控制器节点 |
| `interrupts`           | 描述该设备使用的中断           | 设备节点       |

**`#interrupt-cells`** **的常见值：**

| 控制器类型    | `#interrupt-cells` | 各 cell 含义                               |
| -------- | ------------------ | --------------------------------------- |
| GIC      | 3                  | `<type hwirq flags>`，type: 0=SPI, 1=PPI |
| 简单 GPIO  | 2                  | `<gpio_pin trigger_type>`               |
| 自定义 FPGA | 1 或 2              | 取决于设计                                   |

```dts
                interrupts = <12 IRQ_TYPE_LEVEL_LOW>;
            };
        };

        /* ====== 挂在 FPGA 中断控制器下的设备 ====== */

        fpga_adc: adc@02001000 {
            compatible = "vendor,fpga-adc";
            reg = <0x02001000 0x100>;
            interrupt-parent = <&fpga_intc>;
            interrupts = <3>;    /* FPGA 中断通道 3 */
        };

        fpga_uart: uart@02002000 {
            compatible = "vendor,fpga-uart";
            reg = <0x02002000 0x100>;
            interrupt-parent = <&fpga_intc>;
            interrupts = <5>;    /* FPGA 中断通道 5 */
        };
    };
};
```

**Q：`interrupts`** **和** **`interrupts-extended`** **有什么区别？**

`interrupts` 属性使用当前节点或祖先节点的 `interrupt-parent` 来确定中断控制器。如果一个设备的多个中断分别连接到**不同的控制器**，就需要用 `interrupts-extended`：

```dts
/* 场景：设备有两个中断引脚，分别连接到不同的中断控制器 */
my_complex_device@03000000 {
    compatible = "vendor,complex-dev";
    reg = <0x03000000 0x1000>;

    /* 使用 interrupts-extended 可以为每个中断指定不同的 parent */
    interrupts-extended = <&gic GIC_SPI 89 IRQ_TYPE_LEVEL_HIGH>,
                          <&gpio_a 7 IRQ_TYPE_EDGE_RISING>;

    /* 等价于分别连接到 GIC 的 SPI 89 和 GPIO-A 的 pin 7 */
    interrupt-names = "data-ready", "error";
};
```

**Q：`interrupt-map`** **属性是什么？在什么场景下使用？**

`interrupt-map` 用于总线桥（如 PCIe host bridge）等需要将子设备的中断号翻译到父控制器空间的场景：

```dts
pcie: pcie@10000000 {
    compatible = "vendor,pcie-host";
    #address-cells = <3>;
    #size-cells = <2>;
    #interrupt-cells = <1>;

    interrupt-map-mask = <0x0 0 0 7>;  /* 只关心 INTx 引脚号（低 3 位） */
    interrupt-map = <0 0 0 1 &gic GIC_SPI 100 IRQ_TYPE_LEVEL_HIGH>,  /* INTA → SPI 100 */
                    <0 0 0 2 &gic GIC_SPI 101 IRQ_TYPE_LEVEL_HIGH>,  /* INTB → SPI 101 */
                    <0 0 0 3 &gic GIC_SPI 102 IRQ_TYPE_LEVEL_HIGH>,  /* INTC → SPI 102 */
                    <0 0 0 4 &gic GIC_SPI 103 IRQ_TYPE_LEVEL_HIGH>;  /* INTD → SPI 103 */
};
```

### 代码示例

以下是内核中解析设备树中断信息的关键代码路径：

```c
/* 
 * 内核源码路径：drivers/of/irq.c
 * 当驱动调用 platform_get_irq() 时，最终会调用以下链路：
 */

/*
 * of_irq_parse_one - 解析设备树节点的第 index 个中断
 *
 * 工作流程：
 * 1. 从当前节点找 "interrupts" 或 "interrupts-extended" 属性
 * 2. 确定 interrupt-parent（向上遍历直到找到）
 * 3. 根据 interrupt-parent 的 #interrupt-cells 解析 cell 值
 * 4. 如果经过 interrupt-map 翻译，执行翻译逻辑
 */

/* 驱动中获取中断的标准方式 */
static int my_probe(struct platform_device *pdev)
{
    int irq;

    /* 方式 1：按索引获取（推荐） */
    irq = platform_get_irq(pdev, 0);  /* 获取第 0 个中断 */
    if (irq < 0)
        return irq;  /* 可能是 -EPROBE_DEFER */

    /* 方式 2：按名字获取（如果 DTS 中有 interrupt-names） */
    irq = platform_get_irq_byname(pdev, "data-ready");

    /* 方式 3：手动从 of_node 解析 */
    struct of_phandle_args oirq;
    of_irq_parse_one(pdev->dev.of_node, 0, &oirq);
    irq = irq_create_of_mapping(&oirq);

    return devm_request_irq(&pdev->dev, irq, my_handler, 0, "my_dev", priv);
}
```

### 实战陷阱

1. **`#interrupt-cells`** **数量不匹配导致设备树编译通过但运行时崩溃**

   **故障现象**：内核启动时 panic，backtrace 指向 `irq_domain_xlate_*` 或 `of_irq_parse_one`。
   ```
   [    1.234567] Unable to handle kernel NULL pointer dereference at virtual address 00000008
   [    1.234570] pc : irq_domain_xlate_twocell+0x1c/0x40
   ```
   **根因**：设备树中设备的 `interrupts` 属性 cell 数量与控制器的 `#interrupt-cells` 不一致。例如控制器声明 `#interrupt-cells = <2>`，但设备只写了一个 cell：
   ```dts
   /* 错误：控制器需要 2 个 cell，这里只给了 1 个 */
   my_device {
       interrupt-parent = <&gpio_a>;
       interrupts = <5>;    /* ← 应该是 <5 IRQ_TYPE_EDGE_FALLING> */
   };
   ```
   **排查方法**：
   ```bash
   # 反编译 DTB 检查实际内容
   dtc -I dtb -O dts /sys/firmware/fdt > /tmp/actual.dts
   # 检查中断控制器的 #interrupt-cells 和设备的 interrupts cell 数量
   ```
2. **`interrupt-parent`** **继承机制导致的隐性错误**

   **故障现象**：新增的设备节点的中断怎么也不工作，但设备树编译没有报错。

   **根因**：`interrupt-parent` 是**可继承的**——如果子节点没有显式设置 `interrupt-parent`，会沿着节点树向上找到最近的 `interrupt-parent`。如果某个祖先节点设置了错误的 `interrupt-parent`，所有后代节点都会受影响。
   ```dts
   /* 问题示例 */
   soc {
       interrupt-parent = <&gic>;  /* 所有子节点默认用 GIC */

       subsystem {
           interrupt-parent = <&gpio_a>;  /* 覆盖：子系统下的设备用 GPIO-A */

           my_device@1000 {
               /* 没有显式设置 interrupt-parent */
               /* 继承了 subsystem 的 <&gpio_a> —— 可能不是你期望的！ */
               interrupts = <GIC_SPI 89 IRQ_TYPE_LEVEL_HIGH>;
               /* ← 这里用 GIC 格式写了 3 个 cell */
               /* 但实际 parent 是 gpio_a（#interrupt-cells=2）*/
               /* → 解析错误！ */
           };
       };
   };
   ```
   **最佳实践**：对于挂在非默认中断控制器上的设备，**始终显式指定** **`interrupt-parent`**。

## Q8：中断亲和性（IRQ Affinity）是什么？什么场景需要设置？

### 背景知识

**中断亲和性（IRQ Affinity）** 是指控制中断被分发到哪个 CPU 核心处理的机制。在多核系统中，合理设置中断亲和性可以显著提升性能——尤其在网络密集型、实时系统和 NUMA 架构场景下。

```
默认行为（irqbalance 守护进程自动平衡）：

 CPU 0        CPU 1        CPU 2        CPU 3
 ──────       ──────       ──────       ──────
 网卡 IRQ     USB IRQ      GPIO IRQ     Timer IRQ
 eMMC IRQ                  SPI IRQ

手动绑定亲和性后：

 CPU 0        CPU 1        CPU 2        CPU 3
 ──────       ──────       ──────       ──────
 实时任务     网卡RX-0     网卡RX-1     其他中断
 (无中断)     (专用)       (专用)       (集中处理)
```

### 答题要点

**查看和设置中断亲和性：**

```bash
# 查看 IRQ 62 的当前亲和性掩码
cat /proc/irq/62/smp_affinity
# 输出：f  (即 0b1111，表示可以在 CPU 0-3 上处理)

# 将 IRQ 62 绑定到 CPU 1
echo 2 > /proc/irq/62/smp_affinity   # 0b0010 = CPU 1

# 查看亲和性列表格式（更易读）
cat /proc/irq/62/smp_affinity_list
# 输出：0-3  (所有核)

# 绑定到 CPU 1 和 CPU 3
echo 1,3 > /proc/irq/62/smp_affinity_list
```

**需要设置中断亲和性的三大场景：**

| 场景                | 原因                  | 配置策略                   |
| ----------------- | ------------------- | ---------------------- |
| **网络收包（RSS/RPS）** | 多队列网卡的每个 RX 队列有独立中断 | 每个 RX 队列绑定到不同 CPU 核    |
| **实时系统（RT）**      | 实时任务需要确定性延迟         | 将非 RT 中断隔离到非 RT CPU 核  |
| **NUMA 架构**       | 跨 NUMA 节点访问内存延迟高    | 中断绑定到外设所在 NUMA 节点的 CPU |

### 深入追问

**Q：网络场景下如何配置多队列网卡的中断亲和性？**

```bash
# 查看网卡 eth0 的所有中断
grep eth0 /proc/interrupts
#  80: ... eth0-rx-0
#  81: ... eth0-rx-1
#  82: ... eth0-rx-2
#  83: ... eth0-rx-3

# 分别绑定到不同 CPU 核
echo 1 > /proc/irq/80/smp_affinity   # rx-0 → CPU 0
echo 2 > /proc/irq/81/smp_affinity   # rx-1 → CPU 1
echo 4 > /proc/irq/82/smp_affinity   # rx-2 → CPU 2
echo 8 > /proc/irq/83/smp_affinity   # rx-3 → CPU 3

# 或者使用内核提供的自动配置脚本
# （许多发行版的 irqbalance 已默认处理）
```

数据流经过：

```
网络包到达 → 网卡根据 RSS hash 分到 RX 队列 N → 触发 IRQ
→ 由绑定的 CPU N 处理 → NAPI poll 在同一 CPU 上执行
→ 协议栈处理 → 数据到达 socket → 应用程序在同一 CPU 上读取

关键：整条路径在同一 CPU 上，最大化 cache 命中率
```

**Q：实时系统中如何隔离中断？**

```bash
# 方法 1：内核启动参数隔离 CPU
# 将 CPU 2-3 从调度器和中断中隔离出来，专给实时任务
# 在 cmdline 中添加：
isolcpus=2,3 nohz_full=2,3 irqaffinity=0,1

# irqaffinity=0,1 表示所有中断默认只在 CPU 0-1 上处理
# isolcpus=2,3 表示普通进程不会被调度到 CPU 2-3
# nohz_full=2,3 表示 CPU 2-3 上的 tick 中断也尽量关闭

echo $PID > /sys/fs/cgroup/cpuset/rt_tasks/tasks
```

**Q：GICv3 的 affinity routing 和 GICv2 有什么区别？**

GICv2 使用 `GICD_ITARGETSRn` 寄存器，每个中断用 8 个 bit 的位图指定目标 CPU，最多支持 8 个核。

GICv3 使用 `GICD_IROUTERn` 寄存器，存储目标 CPU 的 **MPIDR affinity 值**（Aff3.Aff2.Aff1.Aff0），理论上支持无限核数：

```c
/* 内核中设置 GICv3 亲和性的代码路径 */
/* drivers/irqchip/irq-gic-v3.c */
static int gic_set_affinity(struct irq_data *d, const struct cpumask *mask_val,
                             bool force)
{
    unsigned int cpu;
    u64 val;

    cpu = cpumask_any_and(mask_val, cpu_online_mask);
    /* 获取目标 CPU 的 MPIDR 值 */
    val = gic_mpidr_to_affinity(cpu_logical_map(cpu));
    /* 写入 GICD_IROUTER 寄存器 */
    gic_write_irouter(val, d->hwirq);

    irq_data_update_effective_affinity(d, cpumask_of(cpu));
    return IRQ_SET_MASK_OK;
}
```

### 代码示例

以下展示在驱动中编程设置中断亲和性：

```c

        cpumask_set_cpu(cpu, &mask);
```

### 实战陷阱

1. **irqbalance 覆盖了手动设置的亲和性**

   **故障现象**：手动设置了 `/proc/irq/N/smp_affinity` 后，过一段时间发现亲和性被改回了默认值。

   **根因**：`irqbalance` 守护进程默认每 10 秒重新平衡一次所有中断的亲和性，会覆盖手动设置。

   **修复方案**：
   ```bash
   # 方案 1：停止 irqbalance
   systemctl stop irqbalance
   systemctl disable irqbalance

   # 方案 2：将特定中断排除在 irqbalance 之外
   # 在 /etc/sysconfig/irqbalance 或 /etc/default/irqbalance 中添加：
   IRQBALANCE_BANNED_IRQS="80 81 82 83"   # 排除这些中断号

   # 方案 3：使用 irq_set_affinity_hint —— irqbalance 会参考 hint
   # 在驱动代码中：
   irq_set_affinity_hint(irq, &desired_mask);
   ```
2. **NUMA 亲和性设置不当导致网络性能下降 50%**

   **故障现象**：一台双路服务器（2 个 NUMA 节点），网卡插在 NUMA 节点 0 的 PCIe 插槽，但所有中断被 irqbalance 分配到了 NUMA 节点 1 的 CPU 上。网络吞吐量只有预期的一半。

   **根因分析**：
   ```
   NUMA 节点 0                 NUMA 节点 1
   ┌──────────────┐            ┌──────────────┐
   │ CPU 0-7      │            │ CPU 8-15     │
   │ 本地内存      │            │ 本地内存      │
   │ PCIe 网卡 ◄──┤──QPI/UPI──→│ 中断处理 ✗   │
   └──────────────┘            └──────────────┘
                                 ↑ 中断在这里处理
                                 → DMA 数据要跨 NUMA 读取
                                 → 延迟增加 ~70ns/次
   ```
   **修复**：
   ```bash
   # 查看网卡所在的 NUMA 节点
   cat /sys/class/net/eth0/device/numa_node
   # 输出：0

   # 查看 NUMA 节点 0 的 CPU 列表
   cat /sys/devices/system/node/node0/cpulist
   # 输出：0-7

   # 将网卡中断绑定到 NUMA 节点 0 的 CPU
   for irq in $(grep eth0 /proc/interrupts | awk '{print $1}' | tr -d ':'); do
       echo 0-7 > /proc/irq/$irq/smp_affinity_list
   done
   ```

## Q9：disable\_irq 和 disable\_irq\_nosync 的区别？

### 背景知识

Linux 内核提供了两种禁用中断的 API，它们在**同步语义**上有关键区别：

```c
/* 源码位置：kernel/irq/manage.c */

/* 同步版本：等待当前正在执行的 handler 完成后才返回 */
void disable_irq(unsigned int irq);

/* 异步版本：立即返回，不等待 handler 完成 */
void disable_irq_nosync(unsigned int irq);

/* 重新使能中断 */
void enable_irq(unsigned int irq);
```

```
disable_irq 的时序：

CPU 0 (调用 disable_irq)          CPU 1 (正在执行 handler)
─────────────────────              ─────────────────────
  disable_irq(62)
       │
       │  设置 IRQ_DISABLED        handler 正在执行...
       │  标志                            │
       │                                  │
       │  ← 自旋等待 ──────────────→     │
       │     (synchronize_irq)            │
       │                                  │
       │                           handler 返回
       │  ← 等待完成                      │
       │
  disable_irq 返回
  （此时可安全假设 handler 不再运行）


disable_irq_nosync 的时序：

CPU 0                              CPU 1
─────                              ─────
  disable_irq_nosync(62)
       │
       │  设置 IRQ_DISABLED
       │
  立即返回 ←──────────────       handler 可能还在执行！
  （handler 可能仍在另一个            │
   CPU 上运行！）                     │
                                handler 返回
```

### 答题要点

| 特性             | `disable_irq`                       | `disable_irq_nosync` |
| -------------- | ----------------------------------- | -------------------- |
| 同步语义           | 等待 handler 完成                       | 不等待                  |
| 安全性            | 返回后可安全释放资源                          | 需额外同步                |
| 可在 hardirq 中调用 | **不可！会死锁**                          | **可以**               |
| 内部实现           | `__disable_irq` + `synchronize_irq` | 仅 `__disable_irq`    |
| 性能             | 可能阻塞数微秒到数毫秒                         | 立即返回                 |

**引用计数机制：**

`disable_irq` 和 `enable_irq` 使用引用计数（`irq_desc->depth`）。这意味着：

```c
disable_irq(62);   /* depth: 0 → 1, 中断被禁用 */
disable_irq(62);   /* depth: 1 → 2, 仍然禁用 */
enable_irq(62);    /* depth: 2 → 1, 仍然禁用！ */
enable_irq(62);    /* depth: 1 → 0, 中断恢复使能 */

/* 如果多调用了一次 enable_irq */
enable_irq(62);    /* depth 已经是 0，内核打印警告：
                      "Unbalanced enable for IRQ 62" */
```

### 深入追问

**Q：为什么** **`disable_irq`** **在 hardirq handler 中调用会死锁？**

```
死锁过程分析：

CPU 0
─────
1. GIC 收到 IRQ 62 → CPU 0 开始执行 handler
2. handler 内部调用 disable_irq(62)
3. disable_irq → synchronize_irq(62)
4. synchronize_irq 检查：IRQ 62 的 handler 是否在某个 CPU 上运行？
5. 是的——就在 CPU 0 上运行（就是我自己！）
6. synchronize_irq 自旋等待 handler 返回...
7. 但 handler 在等待 synchronize_irq 返回...
8. → 死锁！CPU 0 永远卡住

   disable_irq(62)
       ↓
   synchronize_irq(62)
       ↓
   等待 handler 返回 ←──────┐
                            │ handler 在等待
   handler 在执行           │ disable_irq 返回
   disable_irq ──→         ↓
   （永远不返回）    （永远不执行到这）
```

**正确做法**：在 handler 内部使用 `disable_irq_nosync`：

```c
static irqreturn_t my_handler(int irq, void *dev_id)
{
    struct my_device *dev = dev_id;

    /* 在 handler 内部禁用自身中断时，必须用 nosync 版本 */
    disable_irq_nosync(dev->irq);

    /* 安排 work 来做后续处理和重新使能中断 */
    schedule_work(&dev->recovery_work);

    return IRQ_HANDLED;
}

static void recovery_work_fn(struct work_struct *work)
{
    struct my_device *dev = container_of(work, struct my_device, recovery_work);

    /* 在进程上下文中做恢复工作 */
    reset_hardware(dev);

    /* 重新使能中断 */
    enable_irq(dev->irq);
}
```

**Q：`local_irq_disable()`** **和** **`disable_irq()`** **有什么区别？**

| 特性      | `local_irq_disable()`                | `disable_irq(N)`                 |
| ------- | ------------------------------------ | -------------------------------- |
| 作用范围    | 当前 CPU 的所有中断                         | 特定中断号 N                          |
| 影响的 CPU | 仅当前 CPU                              | 所有 CPU                           |
| 实现      | 修改 CPU 的 PSTATE/CPSR                 | 修改 GIC 的 `GICD_ICENABLERn`       |
| 典型用途    | 保护极短的临界区                             | 控制特定设备的中断                        |
| 嵌套      | `local_irq_save`/`local_irq_restore` | `disable_irq`/`enable_irq`（引用计数） |

```c
/* local_irq_disable 用法 */
unsigned long flags;
local_irq_save(flags);       /* 保存中断状态并关中断 */
/* 临界区：所有中断被屏蔽，不可持续太久 */
local_irq_restore(flags);    /* 恢复之前的中断状态 */

/* disable_irq 用法 */
disable_irq(dev->irq);       /* 只禁用特定中断号 */
/* 其他中断仍可正常处理 */
enable_irq(dev->irq);
```

### 代码示例

以下展示安全的中断禁用/使能模式：

```c
#include <linux/interrupt.h>

/* 场景 1：设备挂起时安全禁用中断 */
static int my_suspend(struct device *dev)
{
    struct my_device *mydev = dev_get_drvdata(dev);

    /*
     * 使用 disable_irq（同步版本）：
     * 返回后保证 handler 不再执行，可以安全关闭硬件
     */
    disable_irq(mydev->irq);

    /* 此时可以安全操作硬件，不用担心 handler 并发访问 */
    writel(0, mydev->regs + CTRL_REG);
    clk_disable_unprepare(mydev->clk);

    return 0;
}

/* 场景 2：在中断 handler 中条件性禁用自身 */
static irqreturn_t my_error_handler(int irq, void *dev_id)
{
    struct my_device *dev = dev_id;
    u32 status = readl(dev->regs + STATUS_REG);

    if (status & FATAL_ERROR_BIT) {
        dev_err(dev->dev, "致命硬件错误，禁用中断\n");
        /*
         * 在 handler 中必须用 nosync 版本！
         * 否则 synchronize_irq 会死等自己返回 → 死锁
         */
        disable_irq_nosync(dev->irq);
        schedule_work(&dev->error_recovery_work);
    }

    writel(status, dev->regs + CLEAR_REG);
    return IRQ_HANDLED;
}

/* 场景 3：spinlock + disable_irq 保护共享数据 */
static void my_config_update(struct my_device *dev, u32 new_config)
{
    /*
     * disable_irq 确保 handler 不在执行
     * spin_lock 防止其他 CPU 上的非中断代码并发访问
     */
    disable_irq(dev->irq);
    spin_lock(&dev->config_lock);

    writel(new_config, dev->regs + CONFIG_REG);
    dev->cached_config = new_config;

    spin_unlock(&dev->config_lock);
    enable_irq(dev->irq);
}
```

### 实战陷阱

1. **`disable_irq`** **在 handler 中调用导致硬锁死**

   **故障现象**：系统完全冻结，看门狗超时后复位。复位后检查 ramdump/coredump，发现 CPU 卡在 `synchronize_irq` 的自旋循环中。
   ```
   # Crash dump 分析（以 crash 工具为例）
   crash> bt
   #0  arch_spin_lock
   #1  synchronize_irq+0x48/0x90
   #2  disable_irq+0x24/0x30
   #3  my_irq_handler+0x88/0x100 [my_driver]    ← handler 中调用了 disable_irq
   #4  handle_irq_event_percpu+0x54/0x80
   #5  handle_fasteoi_irq+0xac/0x1a0
   #6  gic_handle_irq+0x60/0xb0
   ```
   **为什么会锁死**：
   - `disable_irq()` 内部会调用 `synchronize_irq()` 等待“该 IRQ 的 handler 全部退出”。
   - 但你现在正处在该 IRQ 的 handler 里调用 `disable_irq()`，等价于“等自己退出”→自旋死锁。
   **怎么处理（工程上常用的两步）**：
   - 立即修复：在 handler 中把 `disable_irq()` 改为 `disable_irq_nosync()`，并把后续恢复/重置逻辑放到 workqueue/thread\_fn 里做。
   - 排查并加固：全局搜一遍驱动是否在 hardirq context 里调用了会 `synchronize_irq()` 的路径（disable\_irq、free\_irq、某些 teardown 流程），必要时加状态机避免重复 disable。
   **怎么分析 crash dump（常用工具与最短路径）**：
   - 获取 dump：服务器/发行版常用 kdump 生成 `vmcore`；嵌入式平台常见有 vendor ramdump、pstore/ramoops、或 watchdog 复位后的内存转储。
   - 工具选择：`crash`（最常用）、或 `gdb`/`drgn`（更偏脚本化分析）。
   - `crash` 常用命令：`bt -a`（看所有 CPU 堆栈，确认是否卡在 `synchronize_irq`）、`log`（找最后的 warning/irq 信息）、`ps`（看线程/中断线程状态）、`irq`（查看 IRQ 统计与 action 链）。
   - 目标结论：定位“哪个 handler 在中断上下文里调用了 disable\_irq”，并回到源码把禁用动作挪到非中断上下文。
     **修复**：将 `disable_irq` 替换为 `disable_irq_nosync`。
2. \*\*disable/enable 引用计数不平衡  -- \*\*

   **故障现象**：设备在某些条件下停止响应中断，`/proc/interrupts` 计数不再增长。但代码中确实调用了 `enable_irq`。

   **根因**：错误处理路径中多调用了一次 `disable_irq` 没有对应的 `enable_irq`：
   ```c
   /* 有 bug 的代码 */
   static int do_operation(struct my_device *dev)
   {
       disable_irq(dev->irq);           /* depth: 0 → 1 */

       int ret = program_hardware(dev);
       if (ret) {
           disable_irq(dev->irq);       /* ← BUG：多余的 disable! depth: 1 → 2 */
           return ret;                   /* 返回时 depth=2 */
       }

       enable_irq(dev->irq);            /* depth: 1 → 0，正常路径 OK */
       return 0;
   }
   /* 错误路径中 depth 变成 2，后续只调一次 enable_irq 也无法恢复 */
   ```
   **排查方法**：
   ```bash
   # 检查中断的禁用深度
   cat /sys/kernel/debug/irq/irqs/62
   # 或
   cat /proc/irq/62/spurious
   # 查找 depth 字段
   ```
   **修复**：确保每条代码路径的 `disable/enable` 严格配对，使用 `goto` 统一错误处理：
   ```c
   static int do_operation(struct my_device *dev)
   {
       disable_irq(dev->irq);

       int ret = program_hardware(dev);
       if (ret)
           goto out_enable;

       ret = verify_hardware(dev);

   out_enable:
       enable_irq(dev->irq);
       return ret;
   }
   ```

## Q10：FPGA 通过一根中断线向 ARM 报告多种事件，驱动如何设计？

### 背景知识

在嵌入式系统中，FPGA 作为协处理器是非常常见的架构。FPGA 内部可能运行多种功能模块（ADC、DMA、通信协议引擎等），但只通过一根中断线连接到 ARM 的 GIC。驱动需要在一根中断线上区分和处理多种不同的事件。

```
FPGA 内部架构：

┌─────────────────────────────────────────────┐
│                    FPGA                      │
│                                              │
│  ┌──────┐  ┌──────┐  ┌──────┐  ┌──────┐    │
│  │ ADC  │  │ DMA  │  │ UART │  │ SPI  │    │
│  │ 模块 │  │ 引擎 │  │ 模块 │  │ 引擎 │    │
│  └──┬───┘  └──┬───┘  └──┬───┘  └──┬───┘    │
│     │         │         │         │          │
│  ┌──┴─────────┴─────────┴─────────┴──┐      │
│  │      中断聚合寄存器 (IRQ_STATUS)    │      │
│  │  bit0: ADC_DONE                    │      │
│  │  bit1: DMA_COMPLETE                │      │
│  │  bit2: UART_RX_READY               │      │
│  │  bit3: SPI_ERROR                   │      │
│  │  ...                               │      │
│  └────────────────┬──────────────────┘      │
│                   │ OR gate                   │
│                   │                           │
└───────────────────┼───────────────────────────┘
                    │
                    │ 一根中断线
                    ▼
              GIC (SPI 50)
```

### 答题要点

有两种设计方案：

**方案一：单 handler + workqueue 分发（简单方案）**

```
IRQ → 单一 handler 读 STATUS 寄存器 → 根据 bit 位调用不同处理函数
```

- 优点：实现简单，代码量小
- 缺点：所有子模块的中断处理耦合在一个驱动中

**方案二：FPGA 注册为 irq\_chip 级联中断控制器（推荐方案）**

```
IRQ → FPGA irq_chip 的 chained handler → 读 STATUS
    → 为每个 bit 生成独立的 virq → 子模块驱动各自 request_irq
```

- 优点：各子模块驱动完全解耦，可独立开发和测试
- 缺点：实现复杂度较高

### 深入追问

**Q：为什么方案二更推荐？具体优势在哪？**

| 对比维度  | 方案一（单 handler）             | 方案二（irq\_chip 级联）             |
| ----- | -------------------------- | ----------------------------- |
| 模块耦合  | 所有子模块在同一驱动中                | 各子模块独立驱动                      |
| 可复用性  | 差——换 FPGA 设计需改驱动           | 好——中断控制器驱动与子模块驱动分离            |
| 设备树描述 | 子模块无法有自己的 `interrupts` 属性  | 子模块可以标准化使用 `interrupt-parent` |
| 中断统计  | `/proc/interrupts` 只显示一个中断 | 每个子中断独立显示                     |
| 调试性   | 差                          | 好——可以单独 disable/enable 某个子中断  |

**Q：清中断的顺序有什么讲究？特别是跨时钟域的情况？**

这是 FPGA 驱动中最经典的坑之一。FPGA 通常运行在自己的时钟域（如 100MHz），而 ARM 通过 AXI/APB 总线访问 FPGA 寄存器。写入清除寄存器后，清除信号需要穿越时钟域同步器（通常是 2-3 级触发器），会有几个 FPGA 时钟周期的延迟。

```
写清除寄存器的时序问题：

ARM 侧                    AXI 总线              FPGA 侧
──────                    ────────              ────────
writel(清除值)
   │
   │ → AXI 写事务 →            │
   │                          │ → 到达 FPGA 寄存器
   │                          │    但跨时钟域同步需要
   │                          │    2-3 个 FPGA 时钟周期
   │                          │
   │ ← AXI 写完成确认 ←       │    ← 此时清除可能还未生效！
   │
   │ 如果此时 handler 返回
   │ EOI → GIC 检查中断线
   │ → 中断线还是有效（清除未生效）
   │ → 再次触发中断！
   │ → 伪中断风暴
```

**解决方案：write-back 读回确认**

```c
static irqreturn_t fpga_irq_handler(int irq, void *dev_id)
{
    struct fpga_device *fpga = dev_id;
    u32 status = readl(fpga->base + FPGA_IRQ_STATUS);

    if (!status)
        return IRQ_NONE;

    /* 写清除寄存器 */
    writel(status, fpga->base + FPGA_IRQ_CLEAR);

    /*
     * 关键：read-back！
     * 读回状态寄存器，确保写清除操作已经通过 AXI 总线
     * 到达 FPGA 并经过跨时钟域同步后生效。
     * 这个 readl 的 AXI 读事务会在 AXI 总线上排在
     * 写事务之后（AXI ordering 保证），返回时
     * 可以保证之前的写已经被 FPGA 处理。
     */
    (void)readl(fpga->base + FPGA_IRQ_STATUS);

    /* 现在可以安全返回 —— 中断线应该已经 deassert */
    process_events(fpga, status);
    return IRQ_HANDLED;
}
```

**Q：如果 FPGA 内部有多级中断聚合怎么办？**

某些复杂 FPGA 设计有两级聚合：

```
Level 2 (子模块内部)              Level 1 (顶层聚合)         ARM
─────────────────                ──────────────           ────
ADC ch0 done ─┐                                          
ADC ch1 done ─┤→ ADC_STATUS ─┐                          
ADC overflow ─┘               ├→ TOP_STATUS ─→ GIC SPI 50
DMA ch0 done ─┐               │                          
DMA ch1 done ─┤→ DMA_STATUS ─┘                          
DMA error    ─┘                                          
```

这种情况可以用**层级 irq\_domain**（hierarchy）来建模：

```dts
fpga_top_intc: interrupt-controller@02000000 {
    compatible = "vendor,fpga-top-intc";
    reg = <0x02000000 0x100>;
    interrupt-controller;
    #interrupt-cells = <1>;
    interrupt-parent = <&gic>;
    interrupts = <GIC_SPI 50 IRQ_TYPE_LEVEL_HIGH>;
};

fpga_adc_intc: interrupt-controller@02001000 {
    compatible = "vendor,fpga-adc-intc";
    reg = <0x02001000 0x100>;
    interrupt-controller;
    #interrupt-cells = <1>;
    interrupt-parent = <&fpga_top_intc>;
    interrupts = <0>;   /* TOP_STATUS 的 bit 0 */
};
```

### 代码示例

**方案一：单 handler + workqueue 分发**

```c
#include <linux/interrupt.h>
#include <linux/workqueue.h>

struct fpga_device {
    void __iomem *base;
    int irq;
    struct work_struct event_work;
    u32 pending_events;
    spinlock_t lock;
};

static irqreturn_t fpga_hardirq(int irq, void *dev_id)
{
    struct fpga_device *fpga = dev_id;
    u32 status;

    status = readl(fpga->base + FPGA_IRQ_STATUS);
    if (!status)
        return IRQ_NONE;

    /* 清中断 + read-back */
    writel(status, fpga->base + FPGA_IRQ_CLEAR);
    (void)readl(fpga->base + FPGA_IRQ_STATUS);

    spin_lock(&fpga->lock);
    fpga->pending_events |= status;
    spin_unlock(&fpga->lock);

    schedule_work(&fpga->event_work);
    return IRQ_HANDLED;
}

static void fpga_event_work(struct work_struct *work)
{
    struct fpga_device *fpga = container_of(work, struct fpga_device, event_work);
    u32 events;

    spin_lock_irq(&fpga->lock);
    events = fpga->pending_events;
    fpga->pending_events = 0;
    spin_unlock_irq(&fpga->lock);

    if (events & BIT(0))
        handle_adc_done(fpga);
    if (events & BIT(1))
        handle_dma_complete(fpga);
    if (events & BIT(2))
        handle_uart_rx(fpga);
    if (events & BIT(3))
        handle_spi_error(fpga);
}
```

**方案二：FPGA 注册为 irq\_chip 级联中断控制器（推荐）**

```c
#include <linux/irqchip.h>
#include <linux/irqdomain.h>
#include <linux/of_irq.h>
#include <linux/platform_device.h>

#define FPGA_MAX_IRQS    16
#define FPGA_IRQ_STATUS  0x00
#define FPGA_IRQ_MASK    0x04
#define FPGA_IRQ_CLEAR   0x08

struct fpga_intc {
    void __iomem *base;
    struct irq_domain *domain;
    int parent_irq;
    raw_spinlock_t lock;
};

/* ======== irq_chip 回调 ======== */

static void fpga_irq_mask(struct irq_data *d)
{
    struct fpga_intc *intc = irq_data_get_irq_chip_data(d);
    unsigned long flags;
    u32 mask;

    raw_spin_lock_irqsave(&intc->lock, flags);
    mask = readl(intc->base + FPGA_IRQ_MASK);
    mask |= BIT(d->hwirq);   /* 对应位置 1 表示屏蔽 */
    writel(mask, intc->base + FPGA_IRQ_MASK);
    raw_spin_unlock_irqrestore(&intc->lock, flags);
}

static void fpga_irq_unmask(struct irq_data *d)
{
    struct fpga_intc *intc = irq_data_get_irq_chip_data(d);
    unsigned long flags;
    u32 mask;

    raw_spin_lock_irqsave(&intc->lock, flags);
    mask = readl(intc->base + FPGA_IRQ_MASK);
    mask &= ~BIT(d->hwirq);  /* 对应位清 0 表示使能 */
    writel(mask, intc->base + FPGA_IRQ_MASK);
    raw_spin_unlock_irqrestore(&intc->lock, flags);
}

static void fpga_irq_ack(struct irq_data *d)
{
    struct fpga_intc *intc = irq_data_get_irq_chip_data(d);

    writel(BIT(d->hwirq), intc->base + FPGA_IRQ_CLEAR);
    /* read-back: 确保清中断写入通过 AXI 总线到达 FPGA 并完成跨时钟域同步 */
    (void)readl(intc->base + FPGA_IRQ_STATUS);
}

static struct irq_chip fpga_irq_chip = {
    .name       = "fpga-intc",
    .irq_mask   = fpga_irq_mask,
    .irq_unmask = fpga_irq_unmask,
    .irq_ack    = fpga_irq_ack,
};

/* ======== irq_domain 回调 ======== */

static int fpga_domain_map(struct irq_domain *d, unsigned int virq,
                            irq_hw_number_t hwirq)
{
    struct fpga_intc *intc = d->host_data;

    irq_set_chip_and_handler(virq, &fpga_irq_chip, handle_edge_irq);
    irq_set_chip_data(virq, intc);
    irq_set_noprobe(virq);

    return 0;
}

static const struct irq_domain_ops fpga_domain_ops = {
    .map   = fpga_domain_map,
    .xlate = irq_domain_xlate_onecell,  /* DTS 中用 1 个 cell 描述中断号 */
};

/* ======== chained handler ======== */

static void fpga_chained_handler(struct irq_desc *desc)
{
    struct fpga_intc *intc = irq_desc_get_handler_data(desc);
    struct irq_chip *chip = irq_desc_get_chip(desc);
    u32 status, mask;

    chained_irq_enter(chip, desc);

    /* 读有效中断：STATUS AND NOT MASK */
    status = readl(intc->base + FPGA_IRQ_STATUS);
    mask = readl(intc->base + FPGA_IRQ_MASK);
    status &= ~mask;

    while (status) {
        int hwirq = __ffs(status);
        generic_handle_domain_irq(intc->domain, hwirq);
        status &= ~BIT(hwirq);
    }

    chained_irq_exit(chip, desc);
}

/* ======== probe ======== */

static int fpga_intc_probe(struct platform_device *pdev)
{
    struct fpga_intc *intc;
    struct device_node *np = pdev->dev.of_node;

    intc = devm_kzalloc(&pdev->dev, sizeof(*intc), GFP_KERNEL);
    if (!intc)
        return -ENOMEM;

    raw_spin_lock_init(&intc->lock);

    intc->base = devm_platform_ioremap_resource(pdev, 0);
    if (IS_ERR(intc->base))
        return PTR_ERR(intc->base);

    /* 初始化：屏蔽所有中断、清除所有 pending */
    writel(0xFFFF, intc->base + FPGA_IRQ_MASK);
    writel(0xFFFF, intc->base + FPGA_IRQ_CLEAR);

    intc->domain = irq_domain_add_linear(np, FPGA_MAX_IRQS,
                                          &fpga_domain_ops, intc);
    if (!intc->domain) {
        dev_err(&pdev->dev, "创建 irq_domain 失败\n");
        return -ENOMEM;
    }

    intc->parent_irq = platform_get_irq(pdev, 0);
    if (intc->parent_irq < 0) {
        irq_domain_remove(intc->domain);
        return intc->parent_irq;
    }

    irq_set_chained_handler_and_data(intc->parent_irq,
                                      fpga_chained_handler, intc);

    dev_info(&pdev->dev, "FPGA 中断控制器初始化完成，支持 %d 个子中断\n",
             FPGA_MAX_IRQS);
    return 0;
}

static const struct of_device_id fpga_intc_of_match[] = {
    { .compatible = "vendor,fpga-intc" },
    { /* sentinel */ },
};
MODULE_DEVICE_TABLE(of, fpga_intc_of_match);

static struct platform_driver fpga_intc_driver = {
    .probe  = fpga_intc_probe,
    .driver = {
        .name = "fpga-intc",
        .of_match_table = fpga_intc_of_match,
    },
};
module_platform_driver(fpga_intc_driver);
```

### 实战陷阱

1. **FPGA 跨时钟域导致的伪中断风暴**

   **故障现象**：FPGA 级联中断在系统运行几分钟后出现 `nobody cared` 被内核禁用。

   **排查过程**：
   ```bash
   # 步骤 1：检查中断统计
   cat /proc/interrupts | grep fpga
   #  50: 1523456  GIC-0  50  Level  fpga-intc
   #  92:    2345  fpga-intc  0  Edge  fpga-adc
   #  93:    1200  fpga-intc  1  Edge  fpga-dma
   # 注意：父中断 50 的计数远大于所有子中断计数之和！

   # 步骤 2：启用 ftrace 追踪
   echo 1 > /sys/kernel/debug/tracing/events/irq/irq_handler_entry/enable
   # 观察发现大量 IRQ 50 触发但 chained handler 读到 STATUS=0

   # 步骤 3：JTAG 连接 FPGA，检查内部信号
   # 发现 IRQ_STATUS 在清除后，由于跨时钟域延迟，
   # ARM 侧看到清除生效了，但实际 FPGA 的中断输出
   # 信号在 AXI 总线返回确认后又短暂拉高了一个周期
   ```
   **根因**：FPGA 内部的中断清除逻辑和中断输出信号之间存在竞争——清除寄存器写入和输出信号更新在不同时钟域，中间有 2 个 FPGA 时钟周期的延迟。在这个延迟窗口内，GIC 可能再次采样到有效电平。

   **为什么父中断计数会远大于子中断之和？**
   - 父中断（接到 GIC 的那根线）是“FPGA 内部所有子事件的 OR”。只要这根线被 FPGA 短暂拉高/拉低到有效电平，GIC 就会记一次父 IRQ。
   - 但 chained handler 里读 `STATUS=0` 说明：CPU 进来时 FPGA 的“可见状态寄存器”已经没有任何子事件置位了（可能被清了、或根本没同步过来）。
   - 这类“不一致”最常见原因就是 CDC：中断输出信号和状态寄存器位不在同一时钟域，且缺少严格的同步/握手，导致 CPU 看到“线有效但状态为空”。
   **硬件侧更根本的修法（强烈建议）**：
   - 对每个子中断状态位做同步（至少两级触发器）到 CPU/AXI 时钟域，再参与 OR 生成父中断输出，避免亚稳态与短脉冲。
   - 清除采用握手：CPU 写 CLEAR 后，FPGA 在同一时钟域内先清状态位，再更新输出；必要时提供“清除完成/版本号”寄存器供软件确认。
   - 若子事件本身是脉冲，先在 FPGA 内部做“脉冲展宽/事件锁存”（直到被 CLEAR），不要把窄脉冲直接 OR 到 GIC。
   **修复方案**：
   ```c
   /* 在 ack 回调中增加足够的延迟确保跨时钟域同步完成 */
   static void fpga_irq_ack(struct irq_data *d)
   {
       struct fpga_intc *intc = irq_data_get_irq_chip_data(d);

       writel(BIT(d->hwirq), intc->base + FPGA_IRQ_CLEAR);

       /* 多次 read-back：确保跨时钟域同步完全完成 */
       (void)readl(intc->base + FPGA_IRQ_STATUS);
       (void)readl(intc->base + FPGA_IRQ_STATUS);  /* 第二次 read-back 作为安全余量 */
   }
   ```
   同时建议 FPGA 设计者修改 RTL：在中断输出信号上增加同步逻辑，确保清除操作在输出信号上同步生效后再 deassert。
2. **FPGA 热加载后中断状态混乱**

   **故障现象**：通过 JTAG 或 partial reconfiguration 更新 FPGA 逻辑后，中断行为异常——要么收不到中断，要么一直收到中断。

   **根因**：FPGA 重新配置后，寄存器恢复到默认值。如果驱动不知道 FPGA 被重新加载，会出现多类“不一致”：
   - irq\_chip 侧缓存的 mask/trigger 配置与 FPGA 实际寄存器不一致（你已经写过一次的配置丢了）。
   - pending/latched 状态不确定：部分寄存器上电默认值可能是 1，或输出引脚在重配置期间产生毛刺，导致父 IRQ 线被误触发。
   - bit 定义变化：热加载更换了 RTL 版本后，某些子中断位含义/编号变化，但 Linux 侧的 irq\_domain mapping 仍然是旧的语义。
   **排查要点**：
   - 在 reload 前后对比 FPGA IRQ\_STATUS/IRQ\_MASK/IRQ\_TYPE 等关键寄存器的值，确认是不是“配置丢失/默认值变化”导致行为改变。
   - 在 reload 期间先 `disable_irq(parent_irq)`，并在 re-init 完成后再 `enable_irq(parent_irq)`，避免毛刺把系统打进风暴。
   **修复方案**：FPGA 热加载后需要重新初始化中断控制器：
   ```c
   /* FPGA 热加载回调 */
   static void fpga_post_reload(struct fpga_intc *intc)
   {
       int i;

       /* 重新初始化 FPGA 中断控制器硬件 */
       writel(0xFFFF, intc->base + FPGA_IRQ_MASK);    /* 先屏蔽所有 */
       writel(0xFFFF, intc->base + FPGA_IRQ_CLEAR);   /* 清所有 pending */

       /* 根据内核侧的状态重新配置 FPGA 的 mask 寄存器 */
       for (i = 0; i < FPGA_MAX_IRQS; i++) {
           unsigned int virq = irq_find_mapping(intc->domain, i);
           if (virq) {
               struct irq_data *d = irq_get_irq_data(virq);
               if (d && !irqd_irq_masked(d)) {
                   /* 该中断在内核侧是使能状态，重新 unmask */
                   fpga_irq_unmask(d);
               }
           }
       }
   }
   ```
3. **chained handler 执行时间过长阻塞其他中断**

   **故障现象**：当 FPGA 多个子中断同时触发时，系统出现明显的中断延迟抖动，影响实时性。

   **根因**：chained handler 在 hardirq 上下文中执行，且本地中断通常是关闭的。如果 FPGA 的 `STATUS` 寄存器读取很慢（AXI 总线延迟大），或者子中断数量多（`while(status)` 循环多次），chained handler 的执行时间可能达到几十微秒，影响其他中断的响应。

   **修复方案**：对于延迟敏感的场景，考虑将 chained handler 改为 threaded handler：
   ```c
   /* 使用 generic_handle_domain_irq_safe 代替 generic_handle_domain_irq */
   /* 或者使用 request_threaded_irq 替代 irq_set_chained_handler */
   static irqreturn_t fpga_threaded_handler(int irq, void *dev_id)
   {
       struct fpga_intc *intc = dev_id;
       u32 status;

       /* 线程上下文：中断已重新使能，不阻塞其他中断 */
       status = readl(intc->base + FPGA_IRQ_STATUS);
       while (status) {
           int hwirq = __ffs(status);
           /* 需要使用 handle_nested_irq 而不是 generic_handle_domain_irq */
           handle_nested_irq(irq_find_mapping(intc->domain, hwirq));
           status &= ~BIT(hwirq);
       }

       return IRQ_HANDLED;
   }

   /* probe 中使用 request_threaded_irq */
   request_threaded_irq(intc->parent_irq, NULL, fpga_threaded_handler,
                         IRQF_ONESHOT, "fpga-intc", intc);
   /* 注意：子中断的 handler 也需要是 nested 类型 */
   ```

## 附录：常用调试命令速查表

```bash
# ====== 中断统计 ======
cat /proc/interrupts                    # 查看所有中断统计
watch -d -n 1 "cat /proc/interrupts"    # 实时监控变化

# ====== 中断亲和性 ======
cat /proc/irq/<N>/smp_affinity          # 查看亲和性掩码

# ====== Spurious 中断检测 ======
cat /proc/irq/<N>/spurious              # 查看 spurious 统计

# ====== irq_domain 调试 ======
ls /sys/kernel/debug/irq/domains/       # 列出所有 irq_domain
cat /sys/kernel/debug/irq/irqs/<N>      # 查看特定 virq 的详细信息

# ====== GIC 寄存器（需要 devmem2 或 JTAG）======
# GICD_ISENABLERn: 中断使能状态
devmem2 <GICD_BASE+0x100+4*n> w
# GICD_ISPENDRn: 中断 pending 状态
devmem2 <GICD_BASE+0x200+4*n> w
# GICD_ISACTIVERn: 中断 active 状态
devmem2 <GICD_BASE+0x300+4*n> w
# GICD_ICFGRn: 触发方式配置
devmem2 <GICD_BASE+0xC00+4*n> w

# ====== ftrace 中断追踪 ======
cd /sys/kernel/debug/tracing
echo irq_handler_entry > set_event       # 追踪所有中断入口
echo "irq==62" > events/irq/irq_handler_entry/filter  # 过滤特定中断
echo 1 > tracing_on
cat trace_pipe                           # 实时查看

# ====== perf 中断分析 ======
perf stat -e irq:irq_handler_entry -a sleep 5          # 5秒内中断总数
perf record -e irq:irq_handler_entry -a -g sleep 10    # 记录中断调用栈
perf report                                              # 分析结果
```
