# 04 - Phase 3：A/B 实验矩阵（一次只改一个旋钮）

本章把“验证假设”的动作固化为实验矩阵。每次实验必须满足：

- 同一场景、同一持续时间、同一采集项
- 至少 3 次重复 run
- 只改一个变量（否则结论不可归因）

建议统一用 [collect_idle_baseline.sh](../../../scripts/power/collect_idle_baseline.sh) 产出数据包，并用 [report_template.md](templates/report_template.md) 固化结果表。

## 3.1 最小实验矩阵（覆盖 A/B/C/D 四桶）

| 实验编号 | 目的 | 变量（唯一变化） | 适用桶 | 关键观测 | 结论判读 |
| --- | --- | --- | --- | --- | --- |
| E1 | 验证深 idle 是否“值得进” | 禁用最深 idle state | B/D | 平均功耗、P99 延迟、深睡驻留/平均驻留 | 禁深睡后抖动显著消失→体验优先可考虑限制深睡；禁深睡功耗大增→先治 wakeup 再保留深睡 |
| E2 | 验证 wakeup 治理收益 | 关闭/合并一个 top wakeup 来源 | A/B | wakeup/s、深睡驻留与平均驻留、功耗变化 | wakeup 降且平均驻留变长→方向正确；wakeup 降但功耗不变→转桶 C 查电源域/互连 |
| E3 | 验证 DVFS 跟随/振荡影响 | 限制频率上限（或固定 governor 对照） | D | cpu_frequency 时间线、功耗、体验指标 | 频率振荡被抑制且体验改善→调频策略/约束是关键路径 |
| E4 | 验证 util 峰值导致频率过冲 | 对后台任务限制 util（uclamp/cgroup） | D | 频率过冲减少、功耗/体验变化 | 过冲减少且功耗下降→可以把后台变“温和”；若体验受损→需按业务白名单 |
| E5 | 验证电源域/互连是否为主导 | 保持软件不变，仅改变测量/供电/温度控制 | C | 功耗仪一致性、genpd/devfreq 状态 | 若功耗结果随测量链路变化大→先修测量与可重复性，再谈优化 |

## 3.2 实验执行规范（团队强约束）

### 运行顺序

- 每个实验：A（baseline）→ B（改动）→ A’（回滚）  
如果 A’ 与 A 差异显著，说明场景不稳定或有残留状态，需要先修复可重复性。

### 每次 run 必须记录

- 场景前置条件（网络/屏幕/温度/充电/后台冻结策略）
- 外部功耗仪参数（采样率/量程/触发/供电电压）
- 采集窗口（开始/结束时间戳）

## 3.3 指标与阈值（Balanced KPI 推荐）

### 待机/续航侧（功耗）

- 平均功耗（mW）：主指标
- wakeup/s：辅助指标（用于解释“为什么睡不深/睡得碎”）
- 深 idle residency（%）与平均驻留（us/ms）：机制指标

### 体验/抖动侧（性能）

按业务选择 1~2 个关键指标作为验收：

- P99 唤醒延迟（从 idle exit 到业务线程可运行的时间）
- 关键交互卡顿计数（例如音频 glitch、触控响应、网络 RTT 尾部）

## 3.4 实验后判读：从数据回到“下一步动作”

按桶给出固定判读路径：

- 桶 A：先解决“为什么深睡不可达”（QoS/tick/runtime PM/domain 条件），不要直接调 state 表
- 桶 B：优先治理 wakeup，让深睡变“长驻留”；不要强行让深睡次数变多
- 桶 C：用 genpd/devfreq/仪器对齐验证“省电路径是否生效”，避免被假象误导
- 桶 D：必须联动看 `cpu_idle`、`cpu_frequency`、`sched`，通过对照实验验证“限制深睡/限制频率/限制 util”的收益与副作用
